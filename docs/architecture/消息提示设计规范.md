# 消息提示设计规范

## 1. 目标

消息提示用于补足用户无法从界面变化中感知的状态，不用于证明每一次操作都“成功了”。

本规范统一 Toast、Alert、加载反馈、删除反馈、失败反馈和手动排序反馈的使用边界，避免页面出现重复、抢眼、不可行动的提示噪音。

## 2. 优先级

选择反馈方式时按以下顺序判断：

1. 界面状态变化：列表项消失、顺序变化、选中态变化、按钮禁用、内容刷新。
2. 局部状态反馈：按钮 loading、行内错误、局部空态、局部 warning。
3. `XMToast`：短驻留、非阻塞、无需用户决策的补充消息。
4. `XMSystemAlert`：破坏性确认、阻断错误、需要用户做选择或确认的场景。

能被用户直接看到的成功结果，默认不再追加 Toast 或 Banner。

## 3. Toast 使用边界

### 3.1 适合使用

- 轻量失败：操作失败但用户可以留在当前页面继续处理。
- warning：当前状态可继续，但需要用户注意限制或风险。
- 不可执行说明：入口被点击后需要解释为什么不能继续。
- 不可见结果：操作结果不在当前视野内，需要短提示补足。
- Undo：结果已经发生，但提供短时间撤销机会。
- 处理中：写操作耗时明显，且页面没有更合适的局部 loading 表达。

### 3.2 不应使用

- 列表项已经消失后再提示“已删除”。
- 排序结果已经稳定后再提示“排序已更新”。
- 保存后页面已经关闭或内容已经更新，再提示“保存成功”。
- 用 Toast 承载需要用户选择、确认或阅读长说明的内容。
- 用顶部 Banner 覆盖导航栏或主要内容，仅为了展示成功消息。

## 4. 删除类操作

- 高风险、不可逆、批量破坏性、删除后影响关联数据的操作，必须先用 `XMSystemAlert` 确认。
- 低风险且有 Undo 的删除，可以直接执行并通过 Toast 提供撤销。
- 删除成功后，优先通过列表项消失、数量变化、空态出现来表达结果。
- 删除失败必须提示原因；可恢复的失败用 `XMToast.error`，需要用户决策或阻断继续操作时用 `XMSystemAlert`。
- 文案必须说明用户下一步能做什么，避免只说“删除失败”。

## 5. 手动排序

- 拖拽中不弹 Toast；反馈来自 Item 抬起、占位、插入位置、自动滚动和复位动效。
- 放手后优先立即稳定到新顺序；顺序变化本身就是成功反馈。
- 排序保存成功默认不显示“排序已更新”“排序已保存”。
- 排序保存耗时明显时，禁用重复拖拽或提交入口，并用局部 loading 或 processing 表达写入中。
- 排序保存失败时必须回滚或刷新到可信顺序，并提示原因，例如“排序保存失败，已恢复原顺序”。
- 数据已变化导致无法提交时，提示“列表已更新，请重新调整顺序”。
- 搜索、筛选、非手动排序、置顶区不可移动等场景必须前置阻断；优先禁用入口或在首次尝试时用 warning 说明原因。
- 批量“移到顶部/底部”若结果在当前界面可见，成功后不显示 Toast；失败或无可移动对象时才提示。

## 6. 加载与写操作反馈

- 读取类加载遵循 `docs/architecture/加载状态反馈基建设计.md`：延迟显示、最短驻留，避免闪烁。
- 写操作必须即时反馈并禁用重复触发入口。
- 写入时间很短时，按钮禁用、局部状态变化即可，不必额外 Toast。
- 写入时间明显时，优先使用局部 loading；只有页面缺少局部承载点时才使用 `XMToast.processing`。
- `processing` 必须由成功静默收口、失败 Toast 或 Alert 收口，不能残留。

## 7. 文案规则

- 短、准、可行动；优先说明限制、失败原因或下一步。
- 不复述用户已经从界面看到的事实。
- 避免把“成功”“已完成”“已更新”作为默认反馈。
- 同一场景只保留一个最清楚的反馈，不叠加 Toast、Banner、Alert 和局部错误。
- 中文文案优先使用自然口语，但不加入情绪化、营销化或玩笑式表达。

## 8. 可访问性与 Reduce Motion

- 如果视觉成功反馈完全依赖动画，Reduce Motion 下必须保留低运动量替代，例如 opacity、状态标记、位置稳定后的可见变化。
- VoiceOver 用户无法可靠感知的结果，可以使用 `UIAccessibility` announcement 补足，例如排序完成、撤销可用、不可执行原因。
- 可访问性 announcement 不等同于视觉 Toast；不要因为需要读屏反馈就给所有用户增加视觉噪音。

## 9. 验收清单

- 成功结果能否直接从界面变化感知？能则不加成功 Toast。
- 失败、不可执行、需要决策的场景是否有明确反馈？
- 写操作是否即时禁用重复触发入口？
- 手动排序是否做到成功静默、失败回滚或解释、不可排序前置阻断？
- 文案是否短且可行动，没有重复界面事实？

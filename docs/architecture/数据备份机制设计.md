# 数据备份机制设计

## 1. 目标

XMNote 的备份包同时承担两类职责：跨 Android/iOS 迁移核心阅读数据库，以及在 iOS 设备之间恢复明确允许迁移的本机偏好。本设计将两者拆成独立归档层，避免为了同步少量设置而导出整个 `UserDefaults`。

当前“设备间同步”指用户通过本地文件、WebDAV 或阿里云盘完成备份与恢复，不包含实时 iCloud 同步。

## 2. 归档分层

统一 ZIP 由 `BackupArchiveService` 生成，三条备份路径共用同一个归档入口。

| 层 | 文件 | 消费端 | 作用 |
| --- | --- | --- | --- |
| 核心数据库 | `xm_note.db`、可选 WAL/SHM | Android、iOS | 书籍、书摘、阅读记录等跨端事实源 |
| Android 兼容偏好 | 既有 SharedPreferences XML | Android | 保留 Android 恢复流程依赖的最小兼容字段 |
| iOS 偏好 sidecar | `xmnote_ios_preferences.json` | 仅 iOS | 恢复经白名单批准的 iOS 本机配置 |

iOS sidecar 是可选附加层。Android 可以忽略它；Android 或旧版 iOS 备份没有该文件时，iOS 仍正常恢复数据库，并保留当前设备偏好。

## 3. 类型化白名单

### 3.1 原则

- 禁止遍历 `UserDefaults.dictionaryRepresentation()` 或导出任意 key/value 字典。
- 每个备份域必须有明确的 `Codable` section、独立版本、导出映射、恢复映射和校验规则。
- 本地物理 key 不直接成为备份协议；sidecar 字段保持稳定，避免重命名 UserDefaults key 破坏历史归档。
- 新增域必须同步登记本文档和术语表，并说明敏感字段、整组/合并策略、缺失字段默认值与高版本处理。
- 当前只有一个独立域，不引入动态注册协议、运行时反射或插件式 registry。出现第二个具备相同扩展模式的域后，再评估公共抽象。

### 3.2 首期白名单

首期只包含完整 AI 配置：

- AI 启用状态；
- 当前服务商；
- DeepSeek 与 SiliconFlow 各自模型；
- AI 释义、选词释义、AI 标签三组 Prompt；
- DeepSeek 与 SiliconFlow 两家 API Key。

Desktop Web 为 Android 兼容保留的 UserDefaults 键不进入该 section，也不参与迁移。

## 4. Sidecar 格式

顶层模型为 `IOSPreferencesBackupEnvelope`：

```json
{
  "formatVersion": 1,
  "aiConfiguration": {
    "sectionVersion": 1,
    "isEnabled": false,
    "provider": "deepSeek",
    "deepSeekModelID": "deepseek-v4-flash",
    "siliconFlowModelID": "deepseek-ai/DeepSeek-V3",
    "prompts": {},
    "deepSeekAPIKey": "<用户配置>",
    "siliconFlowAPIKey": ""
  }
}
```

约束：

- `formatVersion` 管理信封结构，section version 管理单个偏好域。
- sidecar 解压后不得超过 1 MiB；超过限制按偏好附加层损坏处理。
- API Key 以明文进入未加密 ZIP，这是产品明确接受的安全取舍；界面不将备份描述为加密或安全保险箱。
- 原始 JSON、API Key、Prompt 内容不得进入日志、错误文本或分析事件。

## 5. AI 本地配置 v2

`AIConfigurationStore` 使用单个 `ai.configuration.v2` Data 值保存完整 AI 配置和两家 API Key。一次 `UserDefaults.set` 即为该配置的唯一提交点，避免供应商、模型、Prompt 与凭据分散写入后形成混合快照。

迁移规则：

1. 若 v2 已存在，只读取 v2，绝不回退 v1 或 Keychain。
2. 若 v2 不存在，读取 `ai.configuration.v1` 与两家旧 Keychain 凭据。
3. 归一化模型与密钥空白后写入 v2。
4. 仅在 v2 写入成功后删除 v1 和旧 Keychain 项。
5. 读取、保存或创建备份均可触发迁移；`AIConfigurationStore` Actor 负责串行化，取消任务不会提交半份快照。

这条“v2 存在即禁止回退”规则用于防止用户删除密钥后，残留旧 Keychain 数据在未来读取中复活。

## 6. 备份流程

本地文件、WebDAV 与阿里云盘均通过 `BackupRepository.createArchiveArtifact` 进入以下流程：

1. `IOSUserDefaultsBackupCoordinator` 从 `AIConfigurationStore` 获取一致快照；必要时完成旧配置迁移。
2. Coordinator 按白名单构造信封、编码 JSON 并校验 1 MiB 上限。
3. `BackupArchiveService` 在同一个 ZIP 中写入数据库文件、Android 兼容 XML 与 iOS sidecar。
4. 本地路径交给系统文件导出；云端路径将同一归档上传到所选 provider。

API Key 只在内存快照、sidecar 临时文件和最终 ZIP 中出现，所有清理与错误路径均不得打印其内容。

## 7. 恢复顺序与事务边界

恢复顺序固定为：

1. 解压到 staging。
2. 校验数据库版本、Room schema、外键闭包与核心 Record。
3. 捕获当前数据库回滚文件。
4. 关闭当前连接，替换数据库文件并重新打开。
5. 数据库重开成功后，由 Repository 将有效 iOS 偏好 section 整组写入 `ai.configuration.v2`。
6. 返回 `BackupRestoreResult`，由本地和云端入口统一展示结果。

数据库恢复失败时不应用 UserDefaults。偏好恢复发生在数据库成功之后，因此偏好失败不会回滚已经安全恢复的核心阅读数据。

AI section 采用整组替换：

- 空 API Key 会清除当前设备对应密钥；
- 不在当前模型目录中的模型 ID 归一化为该服务商默认模型；
- 配置声明启用、但所选服务商密钥为空时自动关闭 AI；
- 有效信封没有 AI section 时保留当前设备 AI 配置。

## 8. 兼容与部分失败策略

| 场景 | 数据库 | iOS 偏好 | 结果文案 |
| --- | --- | --- | --- |
| 当前格式且 section 有效 | 正常恢复 | 整组恢复 | 数据与设置已恢复。 |
| 无 sidecar 的旧版/Android 备份 | 正常恢复 | 保留当前设备配置 | 数据已恢复。 |
| sidecar 损坏或超过 1 MiB | 正常恢复 | 跳过 | 数据已恢复，部分设置未能恢复。 |
| 信封或 section 版本过高 | 正常恢复 | 跳过 | 数据已恢复，部分设置未能恢复。 |
| 数据库校验、替换或重开失败 | 阻断并按现有流程回滚 | 不变 | 使用核心恢复错误提示 |

偏好错误不得覆盖数据库恢复结果，也不得将内部 JSON 解码错误或敏感字段暴露给用户。

## 9. 版本演进准入

新增或升级备份域时必须同时完成：

1. 新 section 模型与版本常量；
2. 从真实 owner 导出的一致快照；
3. 尺寸、枚举、模型与业务不变量校验；
4. 明确的整组替换或字段合并策略；
5. sidecar 缺失、损坏、当前版本与高版本恢复路径；
6. 敏感字段日志审计；
7. 本地、WebDAV、阿里云三条归档入口验证；
8. 本文档与术语表登记。

只有多个独立域被证明具有相同生命周期和恢复模式后，才允许抽取动态注册基础设施。

## 10. 验收清单

- ZIP 包包含可解析的 `xmnote_ios_preferences.json`，且不包含白名单外 UserDefaults。
- v1 与两家旧 Keychain 凭据只迁移一次；v2 存在后不再回读旧凭据。
- 两家密钥保存、替换和删除互不影响。
- 完整 AI 配置备份后可在另一 iOS 设备整组恢复。
- 空密钥、旧备份无 sidecar、损坏 sidecar和高版本 sidecar符合第 8 节策略。
- WebDAV 与阿里云盘复用本地归档入口，不分别实现 sidecar。
- 日志、错误文本和分析事件中不出现 API Key。

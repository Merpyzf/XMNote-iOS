# 通用状态展示设计规范

## 1. 目标与边界

本规范统一 XMNote 在页面、Sheet、列表背景、卡片和局部内容区中的 Loading、空状态、无搜索结果、异常状态与非阻断失败提示。

统一对象是“展示语义与视觉”，不是业务状态机：

- Repository 继续拥有数据读取与写入事实。
- ViewModel 继续拥有业务阶段、数据快照和错误状态。
- 页面只把真实业务状态映射为通用展示角色。
- 通用组件不访问 Repository、数据库或网络，不推断“是否真的为空”。

源码统一归入 `xmnote/UIComponents/Feedback/StatePresentation/`。该目录只是 `Feedback` 内的源码组件族分组，不是 Swift Package、Framework 或独立构建 Target。

## 2. 状态分类

### 2.1 通用展示角色

`XMStateRole` 只描述内容不可用时的展示语义：

| 角色 | 语义 | 默认 SF Symbol | 使用条件 |
| --- | --- | --- | --- |
| `.instruction` | 等待用户完成前置选择，或说明当前能力不可用等非错误信息 | `info.circle` | 当前没有错误，也不能把状态解释为数据为空 |
| `.empty` | 数据源已确认没有内容 | 无 | 首次读取已经完成，且未处于搜索或筛选无匹配；只有显式传入业务图标时才显示图标 |
| `.noResults` | 搜索或筛选条件下没有匹配内容 | `magnifyingglass` | query 或筛选条件有效，数据源本身不一定为空 |
| `.failure` | 无可用内容且读取失败 | `exclamationmark.triangle` | 错误阻断当前内容展示，可提供一次真实恢复动作 |

业务可以覆盖具有内容辨识度的 SF Symbol，但不能覆盖状态组件的布局、字体、颜色和操作样式。`.empty` 只有在确有前置条件或真实引导价值时才显式传入图标；普通空态保持无图标、无说明、无动作。

内容不存在、已删除或已经失效不是可重试的读取失败。当前统一映射为 `.instruction`，显式使用中性的 `questionmark.circle`，标题直接说明“……不存在或已删除”，不提供无效重试。

### 2.2 展示层级

| 层级 | 组件 | 典型容器 | 是否遮挡已有内容 |
| --- | --- | --- | --- |
| 完整状态 | `XMContentStateView` | 普通页面、Sheet、列表背景 | 当前没有可用主体内容 |
| 紧凑状态 | `XMCompactStateView` | 卡片、分区、局部容器 | 只替代所在局部内容 |
| 非阻断提示 | `XMInlineStatusBanner` | 已有内容上方或下方 | 否，必须保留可信内容 |
| 加载视觉 | `LoadingStateView` | 页面主态、卡片 | 由 `LoadingGate` 或 `LoadPhaseHost` 决定显隐 |

## 3. 状态映射规则

状态映射必须按以下优先级判断：

1. 数据尚未返回：使用 placeholder、业务骨架或经过 `LoadingGate` 控制的 `LoadingStateView`，不得提前显示空态。
2. 数据已返回且搜索或筛选无匹配：使用 `.noResults`。
3. 数据已返回且数据源确实为空：使用 `.empty`。
4. 没有可用内容且读取失败：使用完整或紧凑 `.failure`。
5. 已有可信内容但刷新、分页或写入失败：保留内容，使用 `XMInlineStatusBanner`；不能切换到阻断式失败页。
6. 当前需要用户先选择书籍、范围、日期或完成验证：使用 `.instruction`，不能伪装成 `.empty`。
7. 内容不存在、已删除或已失效：使用无恢复动作的 `.instruction`，不能伪装成 `.failure`。

禁止把“请求尚未结束”映射为“暂无数据”，也禁止把“搜索无匹配”映射为数据源真实为空。

## 4. 组件职责

### 4.1 `XMContentStateView`

- 是生产代码构造 `ContentUnavailableView` 的唯一入口。
- 用于页面、Sheet 和列表背景的完整状态。
- 使用 `ContentUnavailableView` 承载系统不可用内容的容器关系，但四种角色都由组件自定义 label，不能回落到系统默认的粗体大标题。
- 每个状态最多一个低权重文字动作；页面唯一创建、提交或确认动作应留在工具栏或页面操作区。
- 调用方可以决定外层安全区和列表背景接入方式，但不能重新绘制状态视觉。

### 4.2 `XMCompactStateView`

- `.centered` 用于居中的局部空态、无结果、说明态和失败态。
- `.card` 用于确有局部表层边界的卡片或分区状态；组件已经拥有 `CardContainer`，禁止再次套卡。
- 页面级与局部级通过容器、留白和位置区分，不通过缩小或加粗标题制造层级。
- `.card` 动作进入文字列；辅助功能字号下图标与文字自动转为纵向布局。
- 不设置统一固定高度；外层容器负责自身高度、滚动位置和安全区关系。

### 4.3 `XMInlineStatusBanner`

- 用于已有内容仍可继续浏览时的局部说明、警告和失败。
- tone 仅允许 `.neutral`、`.warning`、`.error`。
- 三种 tone 共用中性的 `controlFillSecondary` 弱表层；语义只通过 16pt 图标表达，正文和动作保持中性，不使用警告色或错误色背景、边框。
- 默认字号使用横向尾部动作；辅助功能字号下转为纵向、leading 对齐。
- 页面负责放置位置和外边距，组件不覆盖导航栏或主要内容。

### 4.4 加载组件

- `LoadingStateView` 只统一中性的 `ProgressView` 与可选加载文案，不自行决定何时出现。
- 读取主态使用 `LoadingGate + LoadingStateView` 或 `LoadPhaseHost`。
- `LoadingGate` 的默认读取策略为延迟 150ms、最短驻留 200ms。
- `LoadPhaseHost` 使用 0.16 秒 opacity 转场；Reduce Motion 开启时取消动画但保留状态切换。
- 加载文案使用 `AppTypography.body` Regular 与 `textSecondary`，指示器使用 `textHint`；不使用品牌色制造焦点。
- 按钮加载、上传、导入百分比、扫描、AI 流式输出和业务骨架继续由各自业务 owner 持有。

加载策略的完整约束见 `docs/architecture/加载状态反馈基建设计.md`。

## 5. 视觉与交互规范

### 5.1 排版与图标

- 页面、局部、空数据、无结果、前置条件、失败和内容失效的标题统一使用 `StatePresentationTypography.title = AppTypography.body` Regular 与 `textSecondary`，不得因角色、图标、动作或容器改变字号、字重和颜色。
- 页面和局部居中状态的图标统一为 32pt，局部卡片图标为 18pt，Banner 图标为 16pt；三者都使用 Regular 字重并随对应 Dynamic Type 语义缩放。
- 页面与局部状态说明统一使用 `AppTypography.subheadline` Regular 与 `textHint`；Banner 正文使用 `AppTypography.footnote` Regular 与 `textSecondary`。
- `.failure` 图标使用 `feedbackError`；内容失效图标保持 `textHint`。错误和内容失效不通过标题加粗、放大图标或增加彩色表层强调。
- 装饰性状态图标对 VoiceOver 隐藏；无动作的只读状态可合并朗读，有动作时文案与按钮保持独立焦点。

### 5.2 动作

- `XMContentStateView`、`XMCompactStateView` 与 `XMInlineStatusBanner` 的状态内动作统一为纯文字 `.borderless`，使用专门满足正文级对比度的 `stateActionForeground` 与 Regular 排版；不直接复用品牌填充色 `appTint`，也不使用绿色填充、描边胶囊或重复箭头图标。
- 每个状态最多一个真实动作，例如“重试”“清除筛选”“显示全部”“去验证”。页面已有可见入口时，状态内不重复相同动作。
- 页面唯一的创建、提交或确认动作不提升状态按钮层级，由工具栏或页面操作区承载。
- 组件通过 `xmMinimumHitTarget` 提供至少 44pt 的非视觉命中区；禁止在动作标签内部设置 44pt 可见 frame，避免改变文字按钮的绘制尺寸和布局节奏。
- 禁用状态保留原生 Button 语义；辅助功能字号、长文案和 RTL 下必须自然换行或重排，不能依赖压缩字体。

### 5.3 表层与 Liquid Glass

- 普通页面状态直接属于 `surfacePage` 内容层；局部卡片只在真实局部分组需要边界时使用现有卡片表层。
- Banner 使用中性弱表层，仅图标传递 tone；状态不能只靠颜色区分。
- Liquid Glass 只进入系统导航栏、工具栏和已有浮动功能层 owner。状态正文、状态卡、Banner 和状态动作禁止使用 `.glass`、`.glassProminent`、直接 `.glassEffect` 或自定义玻璃背景。
- 状态组件不通过渐变、阴影、嵌套卡片、装饰插画或品牌色填补空白。

### 5.4 状态切换

- 尺寸与阶段切换节奏统一由 `StatePresentationMetrics` 管理，不在业务页面复制图标尺寸或转场时长。
- 结构性状态切换使用 opacity 或项目既有容器转场，不新增位移、缩放或无限装饰动画。
- Reduce Motion 下取消非必要动画，但必须保留加载、内容、空态和失败之间清楚的结构变化。

## 6. 文案规范与反 AI Slop

- 标题直接陈述事实，优先控制在 4—12 个汉字；短标题和短说明不加句号。
- 说明只在补充用户看不见的原因或下一步时出现，最多一句。能由标题说清时不添加说明。
- 搜索框仍可见时，不重复 query，不添加“换个关键词试试”等模板提示。
- 操作只使用结果明确的真实动作，不使用“好的”“我知道了”等模糊标签。
- 不把数据库、连接、服务器实现细节直接交给用户；失败文案只说明当前任务结果和可执行恢复路径。
- 禁止把“图标 + 标题 + 描述 + 按钮”当作默认模板；按语义从最少信息开始。
- 删除“添加……后会显示在这里”“记录会出现在这里”“当前暂无相关内容”“开启……之旅”“轻松……”“尽情探索”等无行动价值的模板文案。

## 7. 与消息提示的边界

| 场景 | 正确反馈 |
| --- | --- |
| 没有主体内容且无法继续 | `XMContentStateView(role: .failure)` |
| 内容不存在、已删除或失效 | `XMContentStateView(role: .instruction)`，无重试 |
| 卡片或分区无法加载 | `XMCompactStateView(role: .failure)` |
| 已有内容，刷新、分页或写入失败 | `XMInlineStatusBanner` |
| 短驻留、非阻断、无需固定在内容中的消息 | `XMToast` |
| 破坏性确认、阻断错误、需要用户选择 | `XMSystemAlert` |

同一错误只能选择一个最清楚的承载方式，禁止同时叠加完整失败页、Banner、Toast 和 Alert。更多反馈边界见 `docs/architecture/消息提示设计规范.md`。

## 8. 业务 owner 与保留实现

以下状态保留业务所有权，不扩展为 `XMStateRole`，也不强行套入通用组件：

- 根数据库初始化失败等应用启动阻断态。
- OCR 相机权限、受限、设备不可用及相册回退。
- AI 连接、流式输出、部分结果失败、应用失败及专属恢复路径。
- 单个附件上传中、成功、失败和删除重试生命周期。
- 微信读书等批次导入的确定进度、成功、失败和批次语义。
- 与真实容器结构同构的书架骨架、扫码占位、时间线空行、批量选择行等状态。
- 阅读状态时间线等具有业务信息结构的领域状态。
- UIKit 列表背景、`UICollectionView` cell 或特殊容器适配器。

容器适配器只负责布局、生命周期和业务状态映射；只要内部表达的是通用空态、无结果或失败视觉，就必须组合 `XMContentStateView`、`XMCompactStateView` 或 `XMInlineStatusBanner`。业务专用展示可以在 Debug 层复用真实 owner，但不得反向依赖或扩大全局状态角色。

## 9. 工程约束

- `StatePresentation/` 外禁止直接构造 `ContentUnavailableView`。
- 禁止重新引入 `EmptyStateView` 或已删除的页面私有通用状态类型。
- 页面私有 `StateHost` 可以保留业务阶段 switch，但不能自行定义通用状态的图标、字体、间距和按钮样式。
- 通用状态目录禁止使用 Liquid Glass API 和 `.borderedProminent`。
- 生产状态动作保持纯文字；不得为“重试”“重新生成”等已经能独立表达的动作重复添加 SF Symbol。
- 确属容器或领域例外的状态型 View，必须在 `scripts/verify_state_presentations.sh` 的白名单中写明精确路径、类型和原因。

### 9.1 组件扩展决策顺序

当现有状态组件无法贴合新的 UI 设计时，按以下顺序处理：

1. 仅文案、业务图标或业务状态映射不同：继续配置现有组件，不新增视觉类型。
2. 相同容器结构下出现稳定、重复的视觉差异：优先扩展现有组件的 `Style`，并保证默认样式不受影响。
3. 至少两个独立生产场景已经证明相同展示语义、相同结构需求和相同修复模式：允许新增高抽象层级的公共状态组件。
4. 仅服务单一业务工作流、领域时间线、扫描、导入、AI 流程或特殊容器生命周期：继续保留页面私有或领域实现，不进入公共组件族。

“两个独立生产场景”以两个不同的生产 Swift 源文件为最低证据；Debug、Preview、测试目录和同一文件中的两个构造不计入。不能先创建组件再等待未来复用。

### 9.2 新公共组件合同

- 源码必须位于 `xmnote/UIComponents/Feedback/StatePresentation/`。
- 使用通用职责命名，并采用闸门可发现的 `XM…StateView` 或 `XM…StatusBanner` 后缀；`LoadingStateView` 是已有兼容名称。
- 只依赖 SwiftUI、设计令牌和共享展示语义；不得依赖业务模型、Repository、ViewModel、数据库、网络客户端或具体网络状态。
- 适用时复用 `XMStateRole`、`XMStateAction`；新增全局角色同样需要双场景证据，不能为单一页面扩大全局枚举。
- 同步加入 `StatePresentationCatalogView`，覆盖浅色、深色、动态字号、长文案、可用/禁用动作和 Reduce Motion 中适用的组合。
- 同步登记 `docs/architecture/术语对照表.md`、`docs/architecture/UI组件文档清单.md` 和组件指南；组件指南必须列出两个真实生产消费路径。

### 9.3 自动闸门

`scripts/verify_state_presentations.sh` 会自动发现上述命名的公共状态视觉类型，并检查：

- 测试目录存在对应构造样例，且测试中心登记了共享目录入口。
- 术语表、UI 组件文档清单和组件指南已登记。
- 至少两个不同生产源码文件实际构造该组件。
- `StatePresentation/` 外没有直接 `ContentUnavailableView`、旧类型或未审查状态型 View。
- 状态组件共同消费统一标题 token、纯文字无边框动作、非视觉命中区和 Liquid Glass 边界。
- 已审计文案未重新引入模板化提示。

执行静态校验：

```bash
bash scripts/verify_state_presentations.sh
```

## 10. 测试中心视觉验收

Debug 构建可从“我的 → 测试中心 → 状态展示”进入 `StatePresentationTestView`。通用样例直接复用 `StatePresentationCatalogView`，与 SwiftUI Preview 共用一套实现；业务专用样例由 Debug 层组合真实业务 owner，禁止复制一套 Demo 专用状态视觉。

状态展示页按真实语义分组；前四组来自通用目录，业务专用组由 Debug 层组合：

1. 页面状态：安静空态、可操作空态、搜索无结果、前置条件、首次读取失败和内容失效，并保留 missing/failure 对照。
2. 局部状态：居中空态、卡片空态、局部无结果和局部失败。
3. 保留内容状态：中性、警告、错误 Banner，以及带动作、无动作和禁用动作变体；与完全无内容的失败状态分开展示。
4. 加载阶段：placeholder、延迟 loading、card loading 与完整 `LoadPhase`。
5. 业务专用：OCR 权限、AI 部分失败、附件上传和批次导入；由 Debug 层组合，不反向依赖公共目录。

验收控制只覆盖预览区域：

- 外观：系统、浅色、深色。
- 字号：标准、特大、Accessibility 3。
- 宽度：当前、320pt 紧凑宽度、规则宽度。
- 动效：跟随系统 Reduce Motion，并可在预览区域强制开启。
- 阶段：交互切换 placeholder、loading、content、empty、failure。

页面级样例直接渲染在 `surfacePage` 视口，不套通用卡片；局部样例只保留生产组件自身的真实容器，避免双重卡片。样例元信息与状态正文分离，使用固定内存数据，不依赖网络或数据库。

## 11. 验收清单

- 数据尚未返回时是否避免提前闪出空态？
- 数据源为空与搜索无匹配是否分别映射为 `.empty`、`.noResults`？
- 所有通用状态标题是否统一为 `AppTypography.body` Regular 与 `textSecondary`？
- 页面和居中局部图标是否同为 32pt，卡片图标是否为 18pt，Banner 图标是否为 16pt？
- 错误与内容失效是否只通过同尺寸语义图标区分，没有加粗标题或彩色表层？
- 已有内容的刷新失败是否仍保留内容并使用中性 Banner 表层？
- 状态动作是否为纯文字 borderless、使用 `stateActionForeground`，并拥有不改变可见布局的至少 44pt 命中区？
- 页面已有操作入口时，状态内是否避免重复动作？
- 文案是否直接、简短、无模板化引导和技术实现细节？
- 浅色、深色、Increase Contrast、Reduce Transparency、320pt、规则宽度、最长中文、RTL 与 Accessibility 3 是否可用？
- VoiceOver 顺序是否正确，装饰图标是否隐藏，动作是否独立可聚焦？
- Reduce Motion 下是否保留清楚的状态变化且没有位移或缩放动画？
- 状态内容层是否没有 Liquid Glass、嵌套表层和重复品牌强调？
- 新公共组件是否具备两个独立生产消费者，并同步测试目录与治理登记？
- 通用状态闸门和模拟器构建是否通过？

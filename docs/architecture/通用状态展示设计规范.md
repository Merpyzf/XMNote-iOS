# 通用状态展示设计规范

## 1. 目标与边界

本规范统一 XMNote 在页面、Sheet、列表背景、卡片和局部内容区中的 Loading、空状态、无搜索结果、异常状态与非阻断失败提示。

统一对象是“展示语义与视觉”，不是业务状态机：

- Repository 继续拥有数据读取与写入事实。
- ViewModel 继续拥有业务阶段、数据快照和错误状态。
- 页面只把真实业务状态映射为通用展示角色。
- 通用组件不访问 Repository、数据库或网络，不推断“是否真的为空”。

源码统一归入 `xmnote/UIComponents/Feedback/StatePresentation/`。该目录只是 `Feedback` 内的源码组件族分组，不是 Swift Package、Framework 或独立构建 Target。

## 2. 状态分类

### 2.1 通用展示角色

`XMStateRole` 只描述内容不可用时的展示语义：

| 角色 | 语义 | 默认 SF Symbol | 使用条件 |
| --- | --- | --- | --- |
| `.instruction` | 等待用户完成前置选择或操作 | `info.circle` | 当前没有错误，也不能把状态解释为数据为空 |
| `.empty` | 数据源已确认没有内容 | `tray` | 首次读取已经完成，且未处于搜索或筛选无匹配 |
| `.noResults` | 搜索或筛选条件下没有匹配内容 | `magnifyingglass` | query 或筛选条件有效，数据源本身不一定为空 |
| `.failure` | 无可用内容且读取失败 | `exclamationmark.triangle` | 错误阻断当前内容展示，可提供一次主要恢复动作 |

业务可以覆盖具有内容语义的 SF Symbol，但不能覆盖状态组件的布局、字体、颜色和操作样式。

### 2.2 展示层级

| 层级 | 组件 | 典型容器 | 是否遮挡已有内容 |
| --- | --- | --- | --- |
| 完整状态 | `XMContentStateView` | 普通页面、Sheet、列表背景 | 当前没有可用主体内容 |
| 紧凑状态 | `XMCompactStateView` | 卡片、分区、局部容器 | 只替代所在局部内容 |
| 非阻断提示 | `XMInlineStatusBanner` | 已有内容上方或下方 | 否，必须保留可信内容 |
| 加载视觉 | `LoadingStateView` | 页面主态、卡片、行内操作 | 由 `LoadingGate` 或业务写状态决定 |

## 3. 状态映射规则

状态映射必须按以下优先级判断：

1. 数据尚未返回：使用 placeholder、业务骨架或经过 `LoadingGate` 控制的 `LoadingStateView`，不得提前显示空态。
2. 数据已返回且搜索/筛选无匹配：使用 `.noResults`。
3. 数据已返回且数据源确实为空：使用 `.empty`。
4. 没有可用内容且读取失败：使用完整或紧凑 `.failure`。
5. 已有可信内容但刷新、分页或写入失败：保留内容，使用 `XMInlineStatusBanner`；不能切换到阻断式失败页。
6. 当前需要用户先选择书籍、范围或日期：使用 `.instruction`，不能伪装成 `.empty`。

禁止把“请求尚未结束”映射为“暂无数据”，也禁止把“搜索无匹配”映射为数据源真实为空。

## 4. 组件职责

### 4.1 `XMContentStateView`

- 是生产代码构造 `ContentUnavailableView` 的唯一入口。
- 用于页面、Sheet 和列表背景的完整状态。
- 使用系统不可用界面的排版与 `.bordered` 操作。
- 每个状态最多一个主要动作。
- 调用方可以决定外层安全区和列表背景接入方式，但不能重新绘制状态视觉。

### 4.2 `XMCompactStateView`

- `.centered` 用于居中的局部空态或说明态。
- `.card` 用于搜索错误、恢复提示和卡片内失败。
- 不设置统一固定高度；外层容器负责自身高度、滚动位置和安全区关系。
- 标题、说明和动作统一使用 `StatePresentationTypography`。

### 4.3 `XMInlineStatusBanner`

- 用于已有内容仍可继续浏览时的局部说明、警告和失败。
- tone 仅允许 `.neutral`、`.warning`、`.error`。
- tone 只通过图标、背景和边框表达；正文保持可读的中性色。
- 页面负责放置位置和外边距，组件不覆盖导航栏或主要内容。

### 4.4 加载组件

- `LoadingStateView` 只统一视觉，不自行决定何时出现。
- 读取主态使用 `LoadingGate + LoadingStateView` 或 `LoadPhaseHost`。
- `LoadingGate` 的默认读取策略为延迟 150ms、最短驻留 200ms。
- `LoadPhaseHost` 使用 0.16 秒 opacity 转场；Reduce Motion 开启时取消动画但保留状态切换。
- 按钮加载、上传、导入百分比和业务骨架可以继续使用局部 `ProgressView`。

加载策略的完整约束见 `docs/architecture/加载状态反馈基建设计.md`。

## 5. 视觉与交互规范

- 完整状态采用系统 `ContentUnavailableView` 排版，不复制系统标题与说明层级。
- 紧凑状态标题使用 `AppTypography.headlineSemibold`，说明使用 `AppTypography.subheadline`。
- Inline Banner 正文使用 `AppTypography.footnote`，动作使用 `AppTypography.footnoteSemibold`。
- 尺寸和透明度统一由 `StatePresentationMetrics` 管理。
- 间距、圆角、表层和语义色必须复用 `Spacing`、`CornerRadius`、`Color.text*`、`feedbackWarning`、`feedbackError`。
- 普通操作使用系统 `.bordered`，不使用品牌色强调；Inline Banner 操作使用紧凑的 `.borderless`。
- 操作热区不得小于 44pt，长文案必须允许纵向换行。
- 有操作时，文案和按钮保持独立无障碍元素；纯展示状态可合并朗读。
- 结构性状态切换使用 opacity 或项目既有容器转场，不新增位移、缩放或无限装饰动画。

## 6. 与消息提示的边界

| 场景 | 正确反馈 |
| --- | --- |
| 没有主体内容且无法继续 | `XMContentStateView(role: .failure)` |
| 卡片或分区无法加载 | `XMCompactStateView(role: .failure)` |
| 已有内容，刷新或写入失败 | `XMInlineStatusBanner` |
| 短驻留、非阻断、无需固定在内容中的消息 | `XMToast` |
| 破坏性确认、阻断错误、需要用户选择 | `XMSystemAlert` |

同一错误只能选择一个最清楚的承载方式，禁止同时叠加完整失败页、Banner、Toast 和 Alert。更多反馈边界见 `docs/architecture/消息提示设计规范.md`。

## 7. 可以保留的业务实现

以下实现不强行抽入通用状态组件：

- 根数据库初始化失败等应用启动阻断态。
- 与真实容器结构同构的业务骨架。
- 上传、导入百分比、扫描、AI 流式生成等领域工作流状态。
- 阅读状态时间线等具有业务信息结构的领域状态。
- UIKit 列表背景、UICollectionView cell 或特殊容器适配器。

容器适配器只负责布局、生命周期和业务状态映射；只要内部表达的是通用空态、无结果或失败视觉，就必须组合 `XMContentStateView`、`XMCompactStateView` 或 `XMInlineStatusBanner`。

## 8. 工程约束

- `StatePresentation/` 外禁止直接构造 `ContentUnavailableView`。
- 禁止重新引入 `EmptyStateView` 或已删除的页面私有通用状态类型。
- 页面私有 `StateHost` 可以保留业务阶段 switch，但不能自行定义图标、字体、间距和按钮样式。
- 确属容器或领域例外的状态型 View，必须在 `scripts/verify_state_presentations.sh` 的白名单中写明精确路径、类型和原因。

### 8.1 组件扩展决策顺序

当现有状态组件无法贴合新的 UI 设计时，按以下顺序处理：

1. 仅文案、业务图标或业务状态映射不同：继续配置现有组件，不新增视觉类型。
2. 相同容器结构下出现稳定、重复的视觉差异：优先扩展现有组件的 `Style`，并保证默认样式不受影响。
3. 至少两个独立生产场景已经证明相同展示语义、相同结构需求和相同修复模式：允许新增高抽象层级的公共状态组件。
4. 仅服务单一业务工作流、领域时间线、扫描/导入/AI 流程或特殊容器生命周期：继续保留页面私有或领域实现，不进入公共组件族。

“两个独立生产场景”以两个不同的生产 Swift 源文件为最低证据；Debug、Preview、测试目录和同一文件中的两个构造不计入。不能先创建组件再等待未来复用。

### 8.2 新公共组件合同

- 源码必须位于 `xmnote/UIComponents/Feedback/StatePresentation/`。
- 使用通用职责命名，并采用闸门可发现的 `XM…StateView` 或 `XM…StatusBanner` 后缀；`LoadingStateView` 是已有兼容名称。
- 只依赖 SwiftUI、设计令牌和共享展示语义；不得依赖业务模型、Repository、ViewModel、数据库、网络客户端或具体网络状态。
- 适用时复用 `XMStateRole`、`XMStateAction`；新增全局角色同样需要双场景证据，不能为单一页面扩大全局枚举。
- 同步加入 `StatePresentationCatalogView`，覆盖浅色、深色、动态字号、长文案、可用/禁用动作和 Reduce Motion 中适用的组合。
- 同步登记 `docs/architecture/术语对照表.md`、`docs/architecture/UI组件文档清单.md` 和组件指南；组件指南必须列出两个真实生产消费路径。

### 8.3 自动闸门

`scripts/verify_state_presentations.sh` 会自动发现上述命名的公共状态视觉类型，并检查：

- 测试目录存在对应构造样例，且测试中心登记了共享目录入口。
- 术语表、UI 组件文档清单和组件指南已登记。
- 至少两个不同生产源码文件实际构造该组件。
- `StatePresentation/` 外没有直接 `ContentUnavailableView`、旧类型或未审查状态型 View。

执行静态校验：

```bash
bash scripts/verify_state_presentations.sh
```

## 9. 测试中心视觉验收

Debug 构建可从“我的 → 测试中心 → 通用状态展示”进入 `StatePresentationTestView`。该页面直接复用 `StatePresentationCatalogView`，与 SwiftUI Preview 共用一套样例，禁止为测试中心再维护平行目录。

验收控制只覆盖预览区域：

- 外观：系统、浅色、深色。
- 字号：标准、特大、辅助功能字号。
- 动效：跟随系统 Reduce Motion，并可在预览区域强制开启。
- 阶段：交互切换 placeholder、loading、content、empty、failure。

目录中的样例不得以固定外层高度裁切内容；长文案、操作按钮和辅助功能字号必须自然撑开。测试页仅在 `DEBUG` 构建存在，不进入生产导航。

## 10. 验收清单

- 数据尚未返回时是否避免提前闪出空态？
- 数据源为空与搜索无匹配是否分别映射为 `.empty`、`.noResults`？
- 已有内容的刷新失败是否仍保留内容？
- 同语义状态在页面、Sheet、列表背景和卡片中是否使用同一组件族？
- 长错误文案、浅色/深色、辅助功能字号和单一操作是否可用？
- Reduce Motion 下是否保留清楚的状态变化且没有位移或缩放动画？
- 新公共组件是否具备两个独立生产消费者，并同步测试目录与治理登记？
- 通用状态闸门和模拟器构建是否通过？

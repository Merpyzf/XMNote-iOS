# 颜色系统优化规范

用于统一 XMNote 的颜色设计、编码与验收标准，建立「HIG 语义优先 + 品牌表达保留」的可持续体系。

## 1. 背景与目标

当前项目已经把颜色职责拆分到 `SemanticColors.swift` 与 `ColorConstruction.swift`：系统表层优先桥接 Apple 语义色，品牌与业务可视化保留显式调色板，生产路径通过 `DS003` 阻止新的旁路构色。

本规范目标：
- 建立分层颜色架构，明确“系统语义色”和“品牌业务色”边界。
- 提升可访问性与跨版本稳定性。
- 为后续演进提供可执行维护边界与验收闸门。

## 2. 适用范围

- 适用于 `xmnote/` 全量 UI 代码（SwiftUI/UIKit）。
- 默认覆盖浅色、深色、高对比度三类场景。
- `xmnote/Utilities/DesignSystem/SemanticColors.swift` 是项目语义色真相源。
- `xmnote/Utilities/DesignSystem/ColorConstruction.swift` 是 `Color` / `UIColor` 原始构造与桥接的唯一公共入口。

## 3. 颜色分层模型（强制）

### L0 平台语义层（System Semantic）
- 直接来源：Apple 系统语义色。
- 核心颜色：
  - Text: `label`, `secondaryLabel`, `tertiaryLabel`, `quaternaryLabel`
  - Background: `systemBackground`, `secondarySystemBackground`, `systemGroupedBackground`, `secondarySystemGroupedBackground`
  - Fill: `systemFill`, `secondarySystemFill`, `tertiarySystemFill`, `quaternarySystemFill`
  - Separator: `separator`, `opaqueSeparator`
  - Interaction: `link`, `tintColor`
- 目的：平台一致性、自动适配、降低维护成本。

### L1 产品语义层（Product Semantic）
- 基于 L0 封装项目级角色，不按当前色值命名。
- 当前稳定入口：
  - Text：`textPrimary`、`textSecondary`、`textHint`
  - Surface：`surfacePage`、`surfaceCard`、`surfaceNested`、`surfaceSheet`
  - Border：`surfaceBorderStrong`、`surfaceBorderDefault`、`surfaceBorderSubtle`、`surfaceDividerSubtle`
  - Control / Action：`controlFillSecondary`、`primaryActionFill`、`primaryActionForeground`
  - Menu：`menuActionForeground`、`menuSelectedForeground`

### L2 品牌与业务主题层（Brand & Feature Theme）
- 保留产品识别与业务编码色：
  - `brand*`
  - `heatmap*`
  - `readCalendar*`
- 只用于品牌强调和业务可视化，不替代通用文本/背景语义。

### L3 组件语义别名层（Component Alias，可选）
- 仅跨模块复用组件可定义组件别名（如 TopBar/Card/Chart）。
- 页面私有样式不得上升为全局基础令牌。

## 4. 命名与使用规则（强制）

### 4.1 命名规则
- 平台映射按产品角色命名，不把 `systemGray` 等当前外观写入公共名称。
- 品牌/业务主题统一 `brand*`、`readCalendar*`、`heatmap*`。
- 禁止无语义命名：`gray1`、`lightBlack`、`textColor2`。

### 4.2 使用规则
- 正文文本默认使用 `textPrimary` / `textSecondary` / `textHint`。
- 页面与容器背景默认使用 `surfacePage` / `surfaceCard` / `surfaceNested` / `surfaceSheet`。
- 边框与分隔默认使用 `surfaceBorder*` / `surfaceDividerSubtle`。
- 需要显式强调的主交互使用对应 action 或品牌语义。
- 普通导航、工具栏、弹出菜单、列表/卡片行内辅助与装饰性 Icon 默认使用系统前景色或 `iconPrimary`、`iconSecondary`、`textPrimary`、`textSecondary` 等中性色。品牌色仅用于明确的主操作、当前选中态、品牌识别或已定义的业务主题；删除、警告、错误、成功等状态使用对应语义色。禁止仅为提示可点击性或制造装饰强调而给普通 Icon 使用品牌色，与文字并列的辅助 Icon 不得抢占主文本层级。
- 上下文菜单、长按菜单、更多菜单等弹出菜单不属于品牌强调位：普通操作使用系统默认色或 `menuActionForeground`，仅删除、警告等明确语义操作使用对应语义色。
- 页面或根容器设置品牌 `tint` 时，必须检查其对工具栏、菜单及 Icon 的传播；普通菜单与顶部辅助操作使用 `XMMenuLabel`、`xmMenuNeutralTint()`、`xmToolbarNeutralTint()` 或等价中性语义色隔离，禁止依赖根级品牌 `tint` 批量强调所有可交互 Icon。
- 禁止在业务文件直接新增 `Color(...)`、`UIColor(...)` 或私有 hex/adaptive 构造器；确需独立业务调色板时，使用 `Color.xmHex` / `xmAdaptive` / `xmSRGB` 并让功能层拥有语义映射。

### 4.3 禁止误用（重点）
- `brand`、`feedbackWarning`、`feedbackError` 不得直接作为长文本正文前景色。
- 状态信息必须双通道表达：颜色 + 文案/图标，不允许仅靠颜色区分。

## 5. 代码归属与维护边界

### 5.1 `SemanticColors.swift`
- 只承载跨模块稳定角色与经过证明的业务主题色。
- 系统表层通过 `Color.xmResolved` 桥接 UIKit 语义色，不重复写浅色/深色色值。
- 新增成员必须说明前景/背景/状态角色及至少两个使用场景；单页颜色保留在页面或功能 presentation owner。

### 5.2 `ColorConstruction.swift`
- 提供 `Color.xmHex`、`xmAdaptive`、`xmResolved`、`xmSRGB`、`xmRGBAHex` 及对应 `UIColor` 入口。
- 构造 API 不表达业务语义；页面仍应优先使用 `SemanticColors`，不能因为存在 helper 就在调用处散落色值。
- 禁止在其他文件复制同类 hex、adaptive 或 SwiftUI/UIKit bridge 扩展。

### 5.3 功能调色板
- 图表、封面取色或导出渲染等确有独立 owner 的场景，可以在功能层构建颜色。
- Domain 只保留纯值等级或状态；颜色映射位于 UIComponents 或 Views。
- 同一业务调色板在 SwiftUI 与 UIKit 间共享时，必须使用集中桥接入口，避免两套数值漂移。

## 6. 演进流程

1. 先通过 `python3 scripts/design-system/ds.py context --paths <路径>` 确认真相源。
2. 优先复用现有语义色；只有语义缺失且跨场景复用成立时新增 token。
3. 单点功能颜色保留在功能 presentation owner，不上升为全局颜色。
4. 开发中执行 `python3 scripts/design-system/ds.py lint --changed`，收口执行 `python3 scripts/design-system/ds.py audit`。
5. 使用专用模拟器验证真实前景/背景组合的浅色、深色和相关可访问性场景。

## 7. 验收标准

### 7.1 可访问性
- 正文文本对比度 `>= 4.5:1`。
- 大字号文本或强调标题对比度 `>= 3.0:1`。
- 非文本关键边界（按钮/分隔）在深浅色可辨识。

### 7.2 主题一致性
- 浅色与深色模式层级稳定，无“反转感”。
- 高对比度下信息层级仍清晰。

### 7.3 业务表达
- 品牌识别（brand）保持一致。
- 阅读热力图、阅读日历等业务主题色语义不退化。

## 8. 工程闸门与协作要求

### 8.1 静态校验
- `DS003` 阻止生产页面和组件直接构造 `Color` / `UIColor`。
- 颜色定义 owner 仅限 `SemanticColors.swift` 与 `ColorConstruction.swift`；独立功能调色板必须使用公开构造入口并保留明确 owner。
- `ai-build` 与 pre-commit 已接入变更范围检查；全量检查由 `ds.py audit` 完成。

### 8.2 PR 检查单
- 是否使用语义 token，而非外观色值。
- 是否新增颜色误用（背景色做文本色等）。
- 是否补充浅色/深色截图证据（关键页面）。

### 8.3 调试基线
- 使用 `SystemColorsTestView` 作为系统语义色案例基线。
- 用于评审“该颜色是否应迁入系统语义层”。

# Room v45 schema、migration 与 seed 合同漂移

## 问题现象与最小复现

iOS 把开发中的 Notion 结构拆成名为 v45/v46 的两个版本，但 Android 正式 v45 是另一份结构：iOS 缺少 `note_import_hash`，保留 Android 已不存在的字段/索引，并且版本上限、identity 与 seed 也不同。同名版本无法安全互相恢复。

最小复现：分别取 Android 正式 `45.json`、iOS 当时的 v45/v46 canonical 定义和新建实库，对照 `user_version`、identityHash、39 张实体、索引、44→45 migration 及 seed 数量。

## 事实链

- 真实 owner 不是页面或 Record，而是 Android Room 导出的物理合同及 iOS 建库/迁移/恢复三个入口。
- Android 正式 v45 以 `DBConfig.java`、`MIGRATION_44_45.kt` 和 `45.json` 为共同事实源。
- iOS 同名 v45 与开发中 v46 分散定义 schema、migration、restore maximum 和 seed，且不存在 `note_import_hash`。
- 任一入口继续沿用中间合同，都会让 Room identity、版本或表结构失真。

## 根因机制

版本号被当作本地实现名称，而不是跨端不可分割的物理合同；schema、migration、identity、恢复闸门和 seed 又分别维护，导致同名版本不能代表同一个数据库状态。

## 触发条件与影响范围

- 触发：首次建库、v44 升级、Android v45 备份恢复、iOS 备份回到 Android。
- 影响：Notion 同步表、书摘导入去重表、默认资源 seed 和所有跨端恢复判断。
- 不影响：页面展示和 Repository API 形状；旧 iOS v46 仅为未发布开发库，明确通过重建处理。

## 修复策略与取舍

删除错误的开发中 v46 合同，原样同步 Android `45.json`，只保留正式 44→45 migration；统一数据库版本与恢复上限；补齐 `NoteImportHashRecord` 和安全 seed；用 schema hash、identity、实体数量、定向测试和实库 seed 数量共同验收。后来正式 Android v46 到来时重新按同一流程升级，而不是复用旧中间版本。

## 验证证据

- `f643bf59` 记录 11 个数据库/测试文件的合同收敛。
- v40–v45 双端 JSON SHA-256 一致，v45 39 个实体且 identity 正确。
- 定向测试 6/6、Clean 模拟器构建、实库 `user_version` 和 seed 数量均有提交证据。

## 预防与边界

跨端 Room 版本必须把 schema JSON、migration 顺序、identity、seed、恢复上限和 Record/SQL 一起审查。版本号相同不能作为对齐证据，必须验证物理合同和运行结果。

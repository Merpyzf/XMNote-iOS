# 系统弹窗请求重放与展示时序竞态

## 问题现象与最小复现

中心弹窗请求在页面刚挂载、菜单/转场占用 presentation 通道或前一个 alert 正在消失时可能不出现；旧弹窗的 dismiss 回调还可能把已经到来的新请求状态清空。

最小复现：在 `searchable` 键盘退场或已有 presentation 的同一窗口内快速触发 alert，随后关闭占用通道的界面；观察请求是否被重放、是否重复展示以及 dismiss 是否误写新状态。

## 事实链

- 真实 owner 是 `XMSystemAlert` 的 SwiftUI/UIViewControllerRepresentable 桥接，而不是某个调用页面。
- 旧实现每次 update 都通过 `stateProvider` 临时读取布尔值或 item，没有稳定请求身份。
- `presentedAlertController == nil` 只能说明本地引用状态，不能证明 presenter 当前具备展示机会。
- 写入点同时分布在请求状态同步、UIKit present、动作回调和 dismiss 完成回调，存在跨帧竞态。

## 根因机制

实现把“业务仍希望展示”“正在尝试展示”“已经展示”“已经消失”压缩成一个瞬时状态和一个弱引用。SwiftUI 多次更新或 UIKit 转场延迟时，无法判断当前回调属于哪一轮请求，也没有保留因 presenter 暂不可用而失败的 desired state。

## 触发条件与影响范围

- 触发：宿主未进入 window、presenter 已有 presentedViewController、dismiss 尚未完成、同一 item/布尔值快速切换。
- 影响：全部通过 `xmSystemAlert` 进入 UIKit 中心弹窗的生产路径。
- 不影响：直接且确保 presentation 通道空闲的 UIKit imperative 调用；业务动作本身的数据逻辑。

## 修复策略与取舍

为每次展示周期分配 `requestID`，Coordinator 分离 `desiredState`、`activeRequestID`、`lastDismissedRequestID` 与 dismiss in-flight 状态；宿主出现或布局完成时重新 reconcile。只有确认 alert 进入 presentation hierarchy 后才提交 active 状态，旧回调只能关闭对应 requestID。

## 验证证据

- `88f39bf2` 的差异完整覆盖布尔驱动、item 驱动、present、dismiss 和 dismantle 生命周期。
- 后续搜索历史复盘确认 alert 呈现前只稳定 responder，破坏性写入延后到 destructive action。
- Apple 文档确认 alert 本质是通过 presenter 模态呈现的视图控制器，presentation 通道是事实 owner。

## 预防与边界

桥接 UIKit presentation 时必须显式建模请求身份与 desired/attempted/active/dismissed 状态。业务页仍应把确认前的数据保持原样；这条案例不能替代针对 sheet、cover 等其他 presentation 类型的独立证据。

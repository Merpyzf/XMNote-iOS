# 根级搜索宿主范围污染导致阅读页回弹异常

## 问题现象与最小复现

冷启动进入阅读 Tab 时首页下拉回弹正常。进入书摘编辑页或阅读日历再返回，阅读首页与时间线的顶部 overscroll 都会提前终止并直接跳回顶部。进入同一阅读栈内的书籍搜索页后返回可以临时恢复。

最小复现：冷启动 → 阅读首页下拉确认正常 → push `NoteEditorView` 或 `ReadCalendarView` → 返回 → 再次下拉；同时在阅读首页和时间线验证。

## 事实链

- 受害页面分别使用自己的滚动容器，但共同挂在 `MainTabView` 管理的阅读导航栈中。
- `BookSearchView` 是同栈中会重新安装页面级 `searchable` 的页面，也是唯一能让异常复位的路径。
- 真正 owner 是 `MainTabView` 根容器；修复前它对所有 Tab 长期安装 `searchable + tabViewSearchActivation`。
- 写入时机不是滚动过程，而是根视图构建和详情 push/pop 引起的系统搜索宿主重协调。

## 根因机制

根级搜索 modifier 的 owner 范围大于业务需求，使非搜索 Tab 的导航栈也长期持有搜索控制器及其关联系统状态。阅读详情 push/pop 后，这个共享宿主在部分路径中没有完整回落，最终表现为阅读根页回弹异常。页面级搜索能复位只是重新绑定宿主的旁证，不是修复方案。

## 触发条件与影响范围

- 触发：非搜索 Tab 共用根级搜索宿主，且其导航栈发生详情 push/pop。
- 影响：阅读首页、阅读时间线，以及后来复现到的“我的”页面顶部回弹。
- 不影响：冷启动初始状态；搜索 Tab 自身正常的搜索激活；页面私有的内容布局。

## 修复策略与取舍

把根级搜索能力收敛为条件 modifier：只有 `selectedTab == .search` 时才安装 `tabViewSearchActivation` 与 `searchable`，其他 Tab 保持原始 `TabView`。没有修改受害页面的 bounce、布局或导航栏背景，避免用局部补丁掩盖共享 owner 问题。

## 验证证据

- 复现矩阵同时覆盖阅读首页和时间线，并用同栈搜索页/搜索 Tab 两条复位路径交叉证伪。
- `1f863095` 与 `634add4c` 均记录构建成功，后一提交再次恢复同一 owner 边界。
- 详细证据保存在 `docs/feature/搜索交互升级iOS26/阅读页回弹异常复盘.md`。

## 预防与边界

多个根页同时出现系统滚动异常时，先查共同 NavigationStack 和系统 modifier 的 owner 范围。只有出现第二个独立场景且具备同一根因、同一修复策略时，才允许晋升为模式。

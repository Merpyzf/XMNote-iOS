# 搜索交互升级 iOS26 - 设计文档

## 1. 设计概览
- 使用 iOS 26 的 `tabViewSearchActivation(.searchTabSelection)` 作为搜索 Tab 激活策略。
- 搜索输入状态继续由 `MainTabView` 统一管理，但根级搜索宿主只在 `selectedTab == .search` 时挂载。
- `SearchView` 仅负责展示搜索态内容，不再维护输入框状态。
- 搜索历史由公共组件 `XMSearchHistorySection` 渲染，全局搜索与书籍搜索复用同一套 chip、编辑态、删除槽位和清空入口表达。
- 清空历史确认是“决策暂停点”：弹窗出现前先稳定键盘/搜索宿主焦点，确认前不写入历史数据、不退出编辑态、不重排底层上下文。

## 2. 状态设计
- `selectedTab`：当前选中主 Tab。
- `searchQuery`：系统搜索输入绑定。
- `searchPath`：搜索 Tab 自己的 `NavigationStack` 路径。
- `mainTabSearchHost`：`MainTabView` 私有搜索宿主封装，负责按搜索 Tab 激活状态条件挂载系统搜索能力。
- `recentQueries`：全局搜索 ViewModel 暴露的最近搜索词快照，来源于 `GlobalSearchRepository`。
- `isHistoryExpanded` / `isHistoryEditing`：搜索历史区块的本地展示状态，只影响空查询态历史区，不参与搜索结果状态机。
- `clearHistoryConfirmationRequest`：全局搜索页本地清空确认请求，负责在系统搜索焦点释放后呈现 `XMSystemAlertController`。

## 3. 交互流程
1. 用户切到搜索 Tab。
2. `MainTabView` 仅在搜索 Tab 激活时挂载根级 `tabViewSearchActivation(.searchTabSelection)` 与 `.searchable(...)`。
3. 系统搜索输入直接绑定 `searchQuery`，`SearchView` 读取同一份绑定值展示搜索态内容。
4. 用户离开搜索 Tab 后，根级搜索宿主随之卸载，其他导航栈不再继续持有系统搜索控制器状态。

### 3.1 搜索历史编辑流程
1. 空查询态展示最近搜索词。
2. 点击“编辑”后，chip 保持稳定身份，右侧删除操作槽从 0 展开到约 30pt；删除图标以轻微位移和缩放进入。
3. 单条删除直接调用 ViewModel 删除并刷新历史，不走确认弹窗。
4. 点击“完成”退出编辑态并收起历史区。

### 3.2 清空确认流程
1. 点击“清空”后，`MainTabView` 只负责释放系统搜索框焦点，不切换 Tab、不清空搜索词、不关闭搜索宿主。
2. `GlobalSearchView` 持有清空确认 request，并在键盘退场窗口之后用 `XMSystemAlertController` 呈现系统中心弹窗。
3. 弹窗取消时只关闭弹窗，`recentQueries`、`isHistoryEditing` 与 chip 布局保持原样。
4. destructive“清空”确认后才调用 `GlobalSearchViewModel.clearRecentQueries()`，再通过 reset 信号退出历史管理态。

## 4. 视图改造
- `MainTabView`：
  - 搜索 Tab 继续使用现有 `NavigationStack(path: $searchPath)`。
  - 新增 `mainTabSearchHost(isEnabled:searchQuery:)` 私有封装。
  - 只有 `selectedTab == .search` 时才挂载根级搜索宿主。
  - `SearchView` 改为注入 `query` 绑定。
- `SearchView`：
  - 不自带输入框。
  - 只消费 `MainTabView` 提供的 `query` 绑定和结果承载区。
  - 保留 Add 菜单按钮与空态文案。
- `XMSearchHistorySection`：
  - 只负责搜索历史 UI，不持有 Repository 或确认弹窗。
  - chip 的视觉宽度、命中宽度和文本宽度同源计算，避免编辑态进入时整组跳变。
  - 删除按钮始终处在稳定内部结构中，通过右侧操作槽展开/收起表达编辑态。
- `GlobalSearchView`：
  - 本地持有全局搜索清空确认请求，避免把破坏性确认状态挂回 `MainTabView` 根层。
  - 确认弹窗呈现前只释放键盘焦点，不修改搜索 query、历史数据或搜索 Tab 路径。

## 5. 宿主隔离规则
- `searchable`、`tabViewSearchActivation`、`tabBarMinimizeBehavior`、导航栏背景/显示偏好都属于系统宿主状态，不是页面私有布局状态。
- 系统宿主状态必须挂在“最小但正确”的共享 owner 上；能按 Tab 条件隔离时，不能让所有导航栈长期共用同一宿主。
- 当同一条 `NavigationStack` 里既有根页滚动，又有 push 详情页、自定义导航栏或页面内搜索时，优先核对共享容器上的系统 modifier 范围，不要先改根页 `ScrollView`。
- `KeepAliveSwitcherHost` 只负责保活和显隐切换，不承担系统搜索宿主隔离职责。
- 中心确认弹窗属于阻断式决策层，挂载点必须能覆盖当前搜索上下文且不触发底层语义切换；若系统 `.searchable` 正在 active，应先释放 responder，再呈现弹窗。

## 6. 风险与规避
- 风险：根级系统搜索宿主挂载范围过大，导致非搜索 Tab 的导航栈也长期持有搜索控制器状态。
- 风险：多个根页共用同一条导航栈时，某个详情页的 push/pop 可能把系统滚动宿主带入异常状态。
- 风险：清空确认挂在根层并与 `.searchable` 同帧竞争，UIAlertController 抢焦点时会把键盘、Tab 搜索宿主或历史布局变化暴露在弹窗背后。
- 风险：搜索历史 chip 把删除按钮作为条件插入视图，会在编辑态进入时出现宽度突变、淡入闪现和整组重排。
- 规避：按搜索 Tab 条件挂载根级搜索宿主；若同栈出现多个根页同时滚动异常，先排查共享系统 modifier owner，再看页面布局。
- 规避：清空确认前只释放焦点，延后呈现系统弹窗；历史数据写入只放在 destructive 确认动作中。
- 规避：chip 使用稳定内部结构和局部动画，右侧操作槽承担主要动效，Reduce Motion 下减少位移/缩放。

# 阅读计时灵动岛与后台计时实现说明

## 1. 背景与结论

当前 iOS 阅读计时不是“App 后台常驻秒表”。它由三部分共同完成：

- App 内页面用 `ReadingTimerViewModel` 维护前台展示 tick。
- `ReadingTimerRepository` 把 `read_time_record` 作为唯一数据事实源，按 Android 兼容字段保存运行、暂停、待保存、完成和放弃状态。
- Live Activity 由 App 侧 ActivityKit 控制器投射状态，Widget Extension 负责锁屏与灵动岛渲染；运行中的灵动岛数字主要依赖系统 `Text(..., style: .timer)` 按时间锚点自行刷新。

因此，后台或杀进程后的恢复不是依赖 App 继续每秒执行代码，而是依赖数据库快照中的 `elapsed_seconds`、`interrupt_time`、`updated_date`、`start_time` 等锚点重新校准。系统界面则通过 ActivityKit 已提交的 `ContentState` 继续显示可扫读状态。

## 2. Apple 框架原理

Apple 对 Live Activity 的职责拆分很明确：

- App 负责创建、更新、结束 Live Activity。
- Widget Extension 负责使用 SwiftUI/WidgetKit 渲染锁屏、灵动岛 compact、minimal、expanded 等展示形态。
- ActivityKit 负责生命周期管理，包括 request、update、end，以及接收 ActivityKit push。
- Live Activity 的静态数据放在 `ActivityAttributes`，动态数据放在 `ContentState`。

官方文档入口：

- [Displaying live data with Live Activities](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)
- [Animating data updates in widgets and Live Activities](https://developer.apple.com/documentation/widgetkit/animating-data-updates-in-widgets-and-live-activities)
- [Live Activities - Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/live-activities)

需要注意的框架限制：

- Live Activity 每次动态数据更新的 payload 有大小限制，不能把 App 内完整表单状态塞进去。
- Live Activity 有系统生命周期上限，系统可在到达上限后结束活动。
- Widget/Live Activity 环境没有普通 App 进程的自由后台执行能力，Widget Extension 也不能把自己当作网络或定位常驻任务。
- Widget 与 Live Activity 动画有系统约束，例如 Always-On 低亮度场景可能不执行动画。

这些限制决定了阅读计时必须用“轻量状态 + 时间锚点 + 数据库恢复”，而不是用灵动岛承载完整业务状态。

## 3. 当前代码分层

阅读计时相关 owner 如下：

| 层级 | Owner | 职责 |
| --- | --- | --- |
| 页面层 | `xmnote/Views/Reading/ReadingTimerView.swift` | 创建 ViewModel，处理导航、Sheet、弹窗和 `scenePhase` 生命周期。 |
| 状态层 | `xmnote/ViewModels/Reading/ReadingTimerViewModel.swift` | 维护前台 tick、暂停/继续/停止/保存/放弃、恢复冲突和 Live Activity 同步编排。 |
| 数据层 | `xmnote/Data/Repositories/ReadingTimerRepository.swift` | 唯一读写 `read_time_record` 的 Repository，保证 `is_deleted`、状态机、Android 时间字段与统计口径。 |
| 系统桥接 | `xmnote/Infra/LiveActivity/ReadingTimerLiveActivityController.swift` | 使用 ActivityKit 创建、更新、结束阅读计时 Live Activity。 |
| Widget Extension | `xmnoteWidgetExtension/ReadingTimerLiveActivityWidget.swift` | 渲染锁屏和灵动岛各形态。 |
| 跨端偏好 | `xmnote/Services/AndroidSharedPreferencesCompat.swift` | 维护 Android 兼容的 `pending_timing_record_id`。 |
| 恢复兼容 | `xmnote/Database/RestoreCompatibility/StagingIntegrityCanonicalizer.swift` / `TombstoneFactory.swift` | 仅在备份 staging 恢复中处理 tombstone 父行和异常活跃子行软删除。 |

`RepositoryContainer` 在 App 启动后统一注入 `readingTimerRepository`，页面只从 Environment 取 Repository，不直接访问数据库。

## 4. 数据状态机

阅读计时状态定义在 `ReadingTimerRecordStatus`，数值严格对齐 Android `read_time_record.status`：

| 状态 | 数值 | 语义 | 是否未完成 | 是否进入统计 |
| --- | --- | --- | --- | --- |
| `running` | `0` | 正在计时 | 是 | 否 |
| `paused` | `1` | 已暂停 | 是 | 否 |
| `stoppedPendingSave` | `2` | 已结束但待保存 | 是 | 否 |
| `finished` | `3` | 已保存完成 | 否 | 是 |

未完成状态用于冷启动、回前台和深链恢复。只有 `finished = 3` 会进入首页、阅读日历、时间线和书架总时长统计。放弃计时不会把记录推进到 `finished`，而是执行软删除。

## 5. App 内计时链路

### 5.1 开始计时

入口来自阅读页或书籍详情页的阅读计时路由。`ReadingTimerView` 创建 `ReadingTimerViewModel`，并根据入口选择：

- 普通书籍入口：`.book(bookId)`
- Live Activity 深链精确记录入口：`.record(recordId:fallbackBookId:)`
- 全局恢复入口：`.recoverLatest`

用户点击开始后：

1. `ReadingTimerViewModel.start()` 调用 `repository.createSession(bookId:startAt:)`。
2. `ReadingTimerRepository` 在 `read_time_record` 插入一条运行中记录：
   - `status = 0`
   - `elapsed_seconds = 0`
   - `paused_duration_millis = 0`
   - `paused = 0`
   - `is_deleted = 0`
3. 如果书籍不是“在读”，Repository 同步推进书籍阅读状态。
4. ViewModel 应用新会话并启动前台 tick。
5. `ReadingTimerLiveActivityController.start` 创建 Live Activity。
6. `AndroidSharedPreferencesCompat` 写入 Android 兼容的 `pending_timing_record_id`。

### 5.2 前台 tick 与低频快照

前台运行时，`ReadingTimerViewModel.startTicker()` 创建每秒 tick。tick 只负责展示刷新和节流持久化：

- 每秒调用 `handleTick()` 更新 UI 上的 `elapsedSeconds`。
- 每 15 秒调用 `persistRunningSnapshotIfNeeded(at:)` 写一次运行态快照。
- 快照写入时只允许从 `running` 更新到 `running`，避免旧后台任务覆盖暂停或待保存状态。

这意味着 UI 秒表很灵敏，但数据库写入不会每秒发生，降低了 I/O 压力。

### 5.3 暂停与继续

暂停时：

1. ViewModel 用 `currentElapsedSeconds(at:)` 计算当前展示秒数。
2. 用 `currentPausedDurationMillis(at:)` 计算暂停累计。
3. 写入 `status = 1`，并更新 `interrupt_time`、`elapsed_seconds`、`paused_duration_millis`、`paused`、`updated_date`。
4. 同步 Live Activity 更新。

继续时：

1. 补齐本次暂停已经流逝的毫秒数。
2. 写入 `status = 0`，前置状态只允许 `paused`。
3. 重新启动 tick，并同步 Live Activity。

`paused` 字段保留 Android“曾暂停过”的历史语义。只要历史或本次快照出现暂停，保存完成时也不会把它清零。

### 5.4 停止待保存

点击结束时，系统不会立即让记录进入统计，而是进入 `stoppedPendingSave = 2`：

1. 计算当前阅读秒数和暂停累计。
2. 写入 `status = 2`，同时写入 `end_time` 和 `interrupt_time`。
3. 停止 tick。
4. 拉起结束确认 Sheet。
5. 清理 Android pending id，因为 `STOP` 待保存不作为 Android 运行/暂停恢复线索。

这一步的设计意图是防止用户只是点了结束，但还没确认位置、感想、是否读完时，就污染统计数据。

### 5.5 保存完成

用户在结束确认 Sheet 中保存后：

1. `ReadingTimerViewModel.saveFinishedRecord(...)` 停止 tick，并取消后台快照任务。
2. `ReadingTimerRepository.finishSession(...)` 把记录推进为 `status = 3`。
3. 写入结束时间、阅读秒数、暂停累计、阅读位置、记录位置单位、感想。
4. 如有阅读位置，按书籍默认位置单位更新 `book.read_position`。
5. 如用户勾选读完，更新书籍阅读状态为读完。
6. 发出 `readingTimerRecordsDidChange`，供在读首页、时间线等刷新。
7. `ReadingTimerLiveActivityController.end(..., dismissalPolicy: .immediate)` 立即移除系统状态。
8. 清理 Android pending id。

### 5.6 放弃计时

用户选择放弃当前或待恢复未完成计时时：

1. ViewModel 停止 tick，并取消后台快照任务。
2. Repository 执行软删除：
   - `is_deleted = 1`
   - `updated_date = 当前毫秒时间戳`
   - 仅允许 `status IN (0, 1, 2)` 的未完成记录被放弃。
3. 清理页面会话状态。
4. 结束对应 Live Activity。
5. 清理 Android pending id。

放弃不是硬删除。保留软删除记录可以维持跨端同步和备份恢复语义，同时通过所有业务查询的 `is_deleted = 0` 排除统计和 UI 展示。

## 6. 后台与杀进程恢复

### 6.1 进入后台前持久化

`ReadingTimerView` 监听 `scenePhase`：

- `.inactive` / `.background`：调用 `persistBeforeSuspension()`
- `.active`：调用 `refreshAfterResume()`

进入后台前，ViewModel 会把当前展示秒数写入数据库快照，并同步 Live Activity。这个写入只针对当前 ViewModel 管理的未完成记录，避免全局扫描造成误写。

### 6.2 回前台校准

回前台后，恢复逻辑优先顺序是：

1. 如果当前页面已有 `activeSession.id`，按 recordId 重新读取数据库。
2. 如果存在 `pendingRecoverySession`，重新确认它是否仍是未完成状态。
3. 否则按当前 bootstrap mode 重新解析入口。

运行态校准公式在 `calibratedElapsedSeconds(for:at:)`：

```text
elapsed = session.elapsedSeconds + max(0, now - anchor)
anchor = interruptTime ?? updatedDate ?? startTime ?? now
```

因此，即使 App 在后台没有每秒运行，只要进入后台前或低频快照已写入，回前台就能按时间锚点补齐经过时间。

### 6.3 杀进程后恢复

杀进程后，内存中的 `tickerTask` 和 ViewModel 状态都会消失。重新进入页面时：

- Repository 通过 `fetchActiveSession()` 读取全局最新未完成记录。
- 查询只认 `read_time_record.is_deleted = 0`、`status IN (0,1,2)`、有效书籍 `book.is_deleted = 0`。
- ViewModel 用数据库快照重新校准展示时长。
- 如果 Live Activity 仍存在，控制器会更新它；如果不存在，恢复入口允许重新创建。

这也是为什么数据库才是唯一真相，而 Live Activity 只是系统状态投射。

## 7. Live Activity 与灵动岛展示

### 7.1 数据契约

App Target 和 Widget Extension 各自声明同名同字段的 `ReadingTimerActivityAttributes`。字段分为：

静态属性：

- `recordId`
- `bookId`
- `bookName`
- `author`
- `bookCoverURL`

动态状态：

- `status`
- `elapsedSeconds`
- `elapsedText`
- `timerStartDate`
- `bookCoverSnapshotName`
- `updatedAt`

App 侧控制器通过 `makeState(...)` 把业务状态转为 Widget 可消费的轻量状态。`timerStartDate = now - elapsedSeconds`，用于系统 timer 文本从正确锚点继续正计时。

### 7.2 展示形态

Widget Extension 当前覆盖四种展示：

| 展示 | 当前内容 |
| --- | --- |
| Lock Screen | 书籍封面、书名、状态文案、计时文本 |
| Dynamic Island compact leading | 书籍封面 |
| Dynamic Island compact trailing | 计时文本 |
| Dynamic Island expanded leading | 封面、书名、作者或状态 |
| Dynamic Island expanded trailing | 计时文本 |
| Dynamic Island minimal | 书籍封面 |

最小态没有计时数字，因此不存在数字转场问题。compact 和 expanded 的数字都复用 `ReadingTimerIslandElapsedText`。

### 7.3 计时文本策略

`ReadingTimerIslandElapsedText` 的策略是：

- 运行中：
  - compact / expanded 在 1 小时以内使用 `Text(state.timerStartDate, style: .timer)`。
  - lockScreen 始终使用系统 timer 文本。
- 非运行中：
  - 使用 `elapsedText` 或短格式字符串。

所有数字文本都加了：

```swift
.monospacedDigit()
.contentTransition(.numericText(countsDown: false))
```

这里没有强制额外 `.animation(..., value:)`，不属于不合规。Apple 文档把 `.contentTransition(.numericText())` 作为数字内容转场请求，额外动画节奏是视觉调优，不是必须条件。Live Activity/Widget 场景还会受到系统动画时长和 Always-On 低亮度限制。

### 7.4 深链恢复

Live Activity 的 `widgetURL` 使用：

```text
xmnote://reading-timer/{bookId}?recordId={recordId}
```

`MainTabView.handleDeepLink(_:)` 优先使用 `recordId` 进入 `readingSessionRecord`，从而精确恢复真实计时记录。旧链接没有 recordId 时，保留 bookId 入口兼容。

## 8. 软删除与墓碑机制

### 8.1 业务软删除

计时放弃使用业务软删除：

```sql
UPDATE read_time_record
SET is_deleted = 1,
    updated_date = ?
WHERE id = ?
  AND is_deleted = 0
  AND status IN (0, 1, 2)
```

业务软删除的作用：

- 避免放弃的未完成记录进入统计。
- 避免 UI 恢复到已放弃记录。
- 保留跨端同步/备份恢复所需的删除语义。
- 避免硬删导致同步侧无法知道“这条记录被用户放弃”。

所有读取计时上下文和恢复会话的查询都过滤 `is_deleted = 0`。如果记录或关联书籍已被软删除，它就不会被恢复，也不会进入灵动岛。

### 8.2 恢复兼容 tombstone 父行

`TombstoneFactory` 的 tombstone 与上面的业务放弃不是同一个触发场景。

tombstone 父行只在 Android 备份恢复到 iOS 的 staging 整理中生成。目标是修复历史备份里的外键闭包缺口：

1. `StagingIntegrityCanonicalizer` 先补默认根记录。
2. 读取 `PRAGMA foreign_key_check` 结果。
3. 对缺失父记录调用 `TombstoneFactory.ensureParent(...)`。
4. 如果异常子表有 `is_deleted` 字段，则把失去父级的活跃子记录软删除。
5. 整理只发生在 staging 库，不修改原始备份包，也不在普通 App 打开链路执行。

tombstone 父行原则：

- 只为缺失父记录生成。
- 除默认系统占位记录外，合成父行必须是 `is_deleted = 1`。
- 不应进入书架、书籍详情、统计、标签、分组、阅读计时恢复或灵动岛展示。

### 8.3 与阅读计时的关系

阅读计时恢复查询要求：

- `read_time_record.is_deleted = 0`
- `status IN (0,1,2)`
- `book_id != 0`
- 关联 `book.is_deleted = 0`

如果 staging 恢复时某条阅读记录引用了缺失书籍：

- `TombstoneFactory` 可能创建 `book` tombstone 父行以满足物理外键。
- 异常活跃子记录会被软删除。
- 即使父行存在，它也是 `book.is_deleted = 1`，业务查询仍会排除。

因此 tombstone 能保证数据库结构可恢复，但不会把异常历史记录带回阅读计时 UI 或 Live Activity。

## 9. Android 跨端恢复线索

iOS 维护 Android 兼容的 SharedPreferences key：

```text
pending_timing_record_id
```

规则：

- `running` / `paused`：写入当前 record id。
- `stoppedPendingSave` / `finished`：清理 pending id。
- 放弃计时：清理 pending id。
- 导出 Android 可识别 XML 时，pending id 会写成 `<long name="pending_timing_record_id" ... />`。

这保证 iOS 备份恢复到 Android 后，Android 端仍能识别是否存在运行/暂停中的未完成计时。待保存状态不写 pending id，是因为它已经不是“后台继续计时”的恢复线索，而是等待用户确认保存的 App 内业务状态。

## 10. 风险与验证点

### 10.1 杀进程恢复

验证路径：

1. 开始计时。
2. 等待超过 15 秒，确保低频快照至少写入一次。
3. 杀掉 App。
4. 重新进入计时页。

期望：

- 能读取最新未完成记录。
- 展示秒数按 `interrupt_time / updated_date / start_time` 补齐。
- Live Activity 可被更新或重建。

### 10.2 后台恢复

验证路径：

1. 开始计时。
2. 切后台。
3. 等待一段时间。
4. 回前台。

期望：

- `persistBeforeSuspension()` 写入后台前快照。
- `refreshAfterResume()` 重新校准展示时长。
- 灵动岛中的系统 timer 文本继续从锚点展示。

### 10.3 暂停与继续

验证路径：

1. 运行中暂停。
2. 后台停留一段时间。
3. 回前台继续。

期望：

- 暂停期间不增加 `elapsed_seconds`。
- `paused_duration_millis` 补齐暂停经过时间。
- `paused` 历史标记保持为 1。

### 10.4 放弃计时

验证路径：

1. 开始计时后选择放弃。
2. 查看在读首页、时间线、阅读日历统计。
3. 重新进入计时页。

期望：

- `read_time_record.is_deleted = 1`。
- 不进入统计。
- 不再恢复。
- Live Activity 立即结束。
- `pending_timing_record_id` 被清理。

### 10.5 已删除书籍与 tombstone 父书

验证路径：

1. 构造或恢复一条关联 `book.is_deleted = 1` 的未完成计时。
2. 打开计时恢复入口。

期望：

- Repository 不返回该记录。
- 不展示恢复弹窗。
- 不创建 Live Activity。

### 10.6 Live Activity 系统限制

验证点：

- Live Activity 被系统关闭或用户禁用时，App 内计时不受影响。
- ActivityKit 创建/更新失败时不回滚数据库。
- Always-On 低亮度、系统动画限制下，`.numericText` 可能不显示完整动画，但数字展示仍应正确。
- Live Activity 生命周期到达系统上限后，数据库未完成记录仍可通过 App 页面恢复。

## 12. 后续维护原则

- 新增计时状态时，必须同步检查 `ReadingTimerRecordStatus`、Repository SQL、ViewModel 恢复逻辑、Live Activity `status` 字符串映射和 Android 兼容语义。
- 修改 `ContentState` 字段时，必须同时修改 App Target 与 Widget Extension 的同名契约。
- 修改 `is_deleted` 语义时，必须先做 Android/iOS 双端数据库对照，不能只按 iOS UI 需求调整。
- 普通 App 打开链路不得执行 tombstone 修复；tombstone 只能出现在备份 staging 整理中。
- Live Activity 只展示可扫读、轻量、低敏感度信息，不承载结束确认 Sheet、感想输入、阅读位置等 App 内完整状态。

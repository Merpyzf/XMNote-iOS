# AI Bug 经验闭环设计文档

## 1. 设计结论

采用“证据化缺陷 + 双阶段写入 + 渐进门禁 + 精选历史种子”。详细架构、状态机、索引和回滚见 `docs/architecture/AI Bug经验闭环设计.md`。

## 2. 核心流程

```text
Bug 输入 → 分类与脏基线 → 首次生产写入检索并拒绝一次
→ 五项事实闭环 → artifacts 草稿 → 修复与验证 → draft close
→ 用户明确完成 → 正式案例 → validate/audit/eval/治理闸门
```

五项事实是复现、真实 owner、真实写入点、生命周期/调用时机和平台事实来源。

## 3. 数据设计

案例包含现象、复现、owner、写入点、生命周期、平台事实、根因、触发、影响/不影响、策略、验证、保护/例外、路径、提交、复审日期和评分。

根因指纹：模块 + 根因标签 + 触发标签 + 反模式。

修复策略指纹：稳定排序后的策略标签。

两个指纹同时一致，才能说明案例具备模式候选关系。

## 4. Hook 设计

- SessionStart：只注入入口和数量，不注入案例正文。
- UserPromptSubmit：真实 Bug 才建立任务状态；收口消息保留原任务基线。
- PreToolUse：每个新 scope 首次拒绝一次、返回 Top 5 并创建草稿。
- Stop：只比较相对基线产生的保护路径；open 草稿阻断，`stop_hook_active` 放行防循环。

## 5. 检索设计

来源包括正式知识、AGENTS/Skill、架构、学习、踩坑、复盘和 Git。排序先计算真实命中分，再增加种类/状态分。路径只提升同功能域，不允许无关模式填充 Top N。

交互 search 包含 Git 和全文补充；批量 eval 复用同一索引和记录集合，避免 24 次重复扫描。

## 6. 模式与门禁

- candidate：两个独立案例、同根因、同策略、边界明确。
- active：candidate + 用户批准记录。
- enforced：active + 路径存在、mandatory=true 的测试/静态检查/构建 gate/Git Hook。

Git 试运行只对非法知识失败关闭；`fix` 缺 trailer 只告警。30 天后没有用户再次批准，不升级严格 gate。

## 7. 验证

- Python unittest 临时 Git fixture。
- validate/audit/eval。
- JSON、Shell、Skill metadata 与 `git diff --check`。
- 仓库全部治理文档脚本。

App 测试不在用户批准范围内，因此不新增、不运行。

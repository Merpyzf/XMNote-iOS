# Color And Materials

## 目标

让颜色和材质服务业务语义、可读性与信息层级，不根据流行风格或反 AI 清单机械禁用某种颜色。

## 规则

- 优先复用仓库现有语义色、surface 和材质 token；先确认前景、背景、状态与交互语义，再判断是否需要变化。
- 系统蓝、品牌绿、中性色或渐变本身都不是问题。只有具体组合造成语义混淆、机械重复、可读性下降或层级失衡时，才提出修正。
- 不用紫蓝渐变、暗底霓虹、高饱和点缀、发光和重阴影作为默认“高级感”配方。
- 次级文本放在彩色底、玻璃底或材质底上时，通过实际渲染或可复现取值验证可读性；不要只凭颜色名称下结论。
- 分隔、轨道和占位背景应弱于主要内容，但必须在目标外观模式与状态下可辨认。
- 同一信息组内让颜色表达稳定语义；不要混用装饰色、品牌色、选择色、成功色和警告色。
- 上下文菜单、长按菜单、更多菜单等弹出菜单默认保持系统色或项目菜单中性色；普通操作禁止用品牌色强调可点击性，仅删除、警告等明确语义操作使用对应语义色。

## 材质策略

- 内容层默认使用普通表面或现有 surface；不要把玻璃当作万能卡片背景。
- 需要弱化背景时，优先复用系统行为或现有材质，不叠加多层半透明黑白蒙版。
- 阴影只在真实层级或浮起关系需要时使用；如果阴影比内容先被看到，通常应收缩。
- 单点颜色或材质问题保持局部修正。至少两个独立场景证明同根因后，才建议新增全局 token。

## 证据要求

- 对比度通过/失败必须有具体前景与背景、状态、外观模式及测量证据。
- 只有代码、没有截图或运行态时，将颜色观感、振动感、密度和材质层级写为“视觉风险，需截图验证”。

## 反模式

- 看到系统默认色就判定为 AI 味
- 灰字压在彩色底上却没有验证可读性
- 同一页同时出现多套强调语义
- 用玻璃、发光、描边和阴影共同强调一个控件
- 为单页效果创建无复用证据的全局颜色 token

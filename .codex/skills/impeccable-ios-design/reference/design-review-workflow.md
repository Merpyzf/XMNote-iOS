# Design Review Workflow

## 适用范围

用于界面评审、设计方案、发布前抛光和“减弱 AI 感”请求。目标是把审美判断绑定到证据、用户影响和可验证修正，而不是输出风格偏好清单。

## 固定顺序

1. **范围与证据**：说明评审对象、关键用户任务，以及当前拥有截图、预览、运行态还是代码证据。
2. **设计真相源**：读取同模块生产页面、导航关系、设计令牌和已有组件；迁移任务只用 Android 理解业务意图。
3. **问题分类**：区分功能意图、信息架构、视觉层级、交互反馈、组件归位、平台表达和 Liquid Glass 误用。
4. **优先级**：按用户影响排序，先处理会阻断或削弱关键任务的问题。
5. **最小修正**：修到问题真实 owner，保持范围局部；不要把单点问题包装成设计系统改造。
6. **验证方式**：明确需要截图对照、预览尺寸、Dynamic Type、横竖屏、交互路径、可访问性或代码检查中的哪一种。

## 证据规则

- 截图或实际渲染可以支持视觉密度、亲密性、颜色观感和可见层级判断；同时记录设备、尺寸、状态和外观模式等上下文。
- 代码可以支持结构、token、状态分支、点击热区和 API 使用判断，但不能单独证明最终视觉观感。
- 代码无法证明的颜色、密度或层级问题写为“视觉风险，需截图验证”，不得写成已确认缺陷。
- 对比度结论必须来自可复现的前景/背景取值与测量，或明确的运行态证据；只看 token 名称不得断言通过或失败。
- 行为问题先找真实状态 owner、写入点、触发动作和生命周期；未确认时把 owner 写为“待定位”，不要直接给架构方案。
- 涉及 Apple 平台事实时附上 `apple-doc-mcp` 查证结果；工具不可用时只陈述本地代码事实。

## 优先级定义

- **阻塞**：关键任务无法完成，或存在明确的严重可访问性、误操作或平台约束问题。
- **高**：关键任务可以完成，但信息理解、操作发现或反馈明显受损。
- **中**：不阻断任务，但持续削弱层级、可读性、一致性或多尺寸适配。
- **低**：完成度优化；不改变任务理解与结果。

不要使用 7/10、85 分等主观数字评分。没有足够证据时降低结论强度，而不是提高措辞强度。

## 每项发现的输出契约

按以下字段输出每个问题；没有证据的字段明确写“待验证”，不要补造：

- **优先级**：阻塞 / 高 / 中 / 低
- **证据**：截图位置、运行路径或代码位置；注明“已确认”或“视觉风险，需截图验证”
- **用户影响**：说明影响哪个任务、理解或操作
- **真实 owner**：页面、组件、token、状态 owner 或平台行为
- **最小修正**：直接修到 owner 的最小改动
- **验证**：改后如何确认问题消失且没有引入回归

可以先概括当前成立的 1–3 个设计点，但不要用优点冲淡高优先级问题。

## 抽象准入

提出跨页面 token、公共样式、组件或基础设施前，列出至少两个独立场景，并证明它们具有：

1. 相同真实 owner 或根因。
2. 相同修复模式。
3. 独立局部修复会产生真实重复或漂移。

任一条件不成立时，保持局部修正，并在需要时记录后续观察点。

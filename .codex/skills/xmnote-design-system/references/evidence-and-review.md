# 证据与评审

## 证据等级

### Canonical

可以作为设计系统依据，但需同时具备：

- 明确且稳定的真实 owner。
- 至少两个独立生产消费场景，或属于清晰的平台/产品唯一入口。
- 机器目录登记和明确 `useWhen` / `avoidWhen`。
- 与风险相称的 Preview、测试或运行态证据。
- 未与更高优先级仓库事实冲突。

机器策略中的 `allowedPaths` 只表示允许该 owner 使用底层构造器，不证明其中的视觉样式 canonical。token 存在也不等于所有页面都应使用。公共组件身份必须由 catalog 的 `status/useWhen/avoidWhen` 确认。

### 局部成立

单一功能或一组紧密相关页面中已经验证的业务表达。允许继续作为页面级组合或 feature token，但不得因视觉相似直接晋升为全局能力。

### 实验候选

Debug、Preview lab、一次性原型、未形成生产消费者的候选方案。只用于比较和验证，不进入设计真相源，不得复制到生产后再反向宣称“已有规范”。

### 历史异常

孤立实现、重复组件、绕过 token、与平台或当前 canonical 模式冲突的生产遗留。上线事实不等于设计质量；此类实现不得被后续 AI 当作范例。

文档中出现已退役 token、旧 API 或过期组件统计时也按历史证据处理。先查 `policy.json`、真实符号和 Git 历史，不把文档文字直接迁入 Skill。

## 防止丑陋或未成熟设计污染

出现以下情况时停止晋升或复用，并提供局部、可验证的替代：

- 不能说明样式服务哪个用户任务、信息层级或状态语义。
- 主要理由只是“更高级”“更有设计感”“更像某个平台”或“另一个页面也这么写”。
- 通过品牌色、玻璃、阴影、渐变、圆角或装饰图表代替信息组织。
- 为追求整齐把不同重要度内容做成同权卡片，或以卡片嵌套补救亲密性问题。
- 新抽象只能依靠不断增加开关、枚举和可选槽位覆盖差异。
- 缺少截图或实际渲染，却对密度、颜色、材质或层级作确定性判断。

不能只用“丑”作为结论。必须说明证据、用户影响、真实 owner 和最小修正；如果证据不足，降低结论强度而不是提高措辞强度。

## 视觉证据

- 截图或实际渲染可以证明密度、亲密性、颜色观感、可见层级和容器关系；记录设备、尺寸、状态、外观模式和 Dynamic Type。
- 代码可以证明组件、token、固定 frame、状态分支、交互语义和结构风险，但不能单独证明最终观感。
- 对比度判断需要明确前景、背景、状态、外观模式和测量结果。
- 平台行为结论需要 Apple 官方事实；工具不可用时只报告本地代码事实。

用户限定证据范围时，限制的是可用证据，不是结论质量门槛。只读单文件的审查必须先声明“已读范围 / 未核对范围 / 结论上限”；可以确认该文件中的 token、组件、固定尺寸、状态分支和交互语义，不能据此确认完整设计系统合规或最终视觉观感。需要更多证据时列出截图、状态或 owner，而不是静默越界读取。

## 评审顺序

1. 说明评审对象、关键用户任务和现有证据。
2. 读取目标页面、同模块成熟页面、token、机器目录和候选组件。
3. 区分功能意图、信息架构、视觉层级、交互反馈、组件归位和平台表达。
4. 按用户影响排序，先处理阻断关键任务、误操作和可访问性问题。
5. 修到真实 owner，单点问题不包装成设计系统改造。
6. 为每项发现给出改后验证方式。

### 评审轴

只检查任务涉及的轴，但不要用一个轴的结论代替另一个：

| 轴 | 核心问题 | 主要证据 |
| --- | --- | --- |
| 用户任务 | 主任务、退出和失败恢复是否清楚 | 路由、状态 owner、运行路径 |
| 信息层级 | 主内容、支撑信息和元数据是否可区分 | 截图、排版/颜色/空间关系 |
| 排版 | 文本角色与 token 是否匹配，Dynamic Type 是否成立 | Typography owner、最长文案、渲染 |
| 布局 | 亲密性、对齐、容器和安全区是否表达正确关系 | 代码结构、尺寸矩阵、截图 |
| 色彩与材质 | 语义、tint 传播、表层和玻璃层级是否正确 | token owner、真实前景背景、浅深色 |
| 组件 | 是否复用 canonical，是否命中 `avoidWhen` | catalog、生产消费者、依赖方向 |
| 交互反馈 | 控件语义、热区、加载、错误和决策成本是否匹配 | 状态分支、可访问性树、运行操作 |
| 平台表达 | push/cover/sheet、系统控件和 Apple 行为是否正确 | 路由 owner、Apple 官方事实、运行态 |

严重度按用户影响而非审美强度判断：阻断主任务、造成误操作、数据风险或关键可访问性失败为阻塞/高；稳定性较低但仍能完成任务的层级与一致性问题为中；纯完成度且有渲染证据的问题为低。没有截图的主观观感不得升为确定性高优先级缺陷。

## 每项发现的输出合同

- **优先级**：阻塞 / 高 / 中 / 低。
- **证据**：截图、运行路径或代码位置，并注明“已确认”或“视觉风险，需截图验证”。
- **用户影响**：影响的任务、理解、操作或可访问性。
- **真实 owner**：页面、组件、token、状态 owner 或平台行为。
- **最小修正**：直接修到 owner 的最小改变。
- **验证**：改后如何确认问题消失且没有回归。

不要使用主观数字评分。可以概括少量已经成立的设计点，但不能用优点冲淡高优先级问题。

评审是只读任务时，不把发现自动转为大规模治理改造。用户要求实现后，仍按真实 owner 和最小修改范围重新走工作流。

## 抽象准入证明

提出公共 token、样式、组件或基础设施前，列出至少两个独立生产场景，并证明：

1. 相同真实 owner 或根因。
2. 相同状态边界与修复模式。
3. 局部修复会产生真实重复或漂移。
4. 新接口比页面私有组合更能限制错误实现。

任一项不成立时保持局部，并把后续可能复用的方向记录为观察点，而不是提前建立公共能力。

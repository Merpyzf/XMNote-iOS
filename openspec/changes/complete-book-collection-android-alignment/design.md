## Context

iOS 书单模块当前真实 owner 分布如下：

- 书单首页状态：`xmnote/ViewModels/Book/BookCollectionListViewModel.swift`
- 书单详情页面：`xmnote/Views/Book/BookCollectionDetailView.swift`
- 书单详情状态：`xmnote/ViewModels/Book/BookCollectionDetailViewModel.swift`
- 书单 UI 私有组件：`xmnote/Views/Book/Components/BookCollectionVisualComponents.swift`
- 书单 Sheet：`xmnote/Views/Book/Sheets/BookCollectionSheets.swift`
- 书单 Repository：`xmnote/Data/Repositories/BookRepository+Collections.swift`
- 书籍选择器模型与查询：`xmnote/Domain/Models/BookPickerModels.swift`、`xmnote/Data/Repositories/BookReadQuery.swift`

Android 对照事实：

- 手动书单添加入口使用 `showBookSearchSheet`，搜索来源为 `BOTH`，支持手动创建和多选，在线/手动结果可作为 `isDeleted = 1` 的书单占位书保存。
- 书单详情对 `isDeleted = 1` 的书籍显示可加入阅读的状态，点击角标调用 `addBookToRead`。
- 微信读书书单导入通过系统分享识别链接，解析标题、简介、书名、作者、封面和推荐语，并保存为包含占位书的书单。
- 当前书单批量导出会将当前书单内书籍 ID 传给通用书籍批量导出页。
- 书单分享会生成长图，包含书单标题、简介、数量、书籍信息、评分和 relation 推荐语。
- 年度书单编辑页禁用标题但允许编辑简介；iOS 已经把单本书 relation 文本区分为普通书单 `收藏理由` 和年度书单 `年度点评`。
- Android 会记住书单首页显示 `我的书单` 还是 `年度书单`。

本设计承接上一轮 `align-book-collection-export-annual-notes` 的结果：iOS 已经有 `导出此书单` 占位入口，年度书单也已经支持单本书 `年度点评`。本次计划聚焦剩余真实能力，不重复改写已经成立的 UI 语义。

## Goals / Non-Goals

**Goals:**

- 一次性覆盖 Android 端书单模块剩余未对齐能力，避免后续反复发现缺口。
- 将书单添加链路扩展为本地、在线、手动创建、多选，并支持书单占位书。
- 让占位书在 iOS 端可理解、可打开、可恢复到书架或阅读。
- 支持微信读书书单导入，并用 iOS 预览确认流程改进 Android 直接创建的风险。
- 将 `导出此书单` 从占位反馈升级为真实当前书单导出。
- 支持书单分享长图或视觉卡片，保留 relation 文本表达。
- 为年度书单提供本体级 `年度寄语` 或 `年度说明`，并与单本书 `年度点评` 区分。
- 记住书单首页最近选择的书单分组。

**Non-Goals:**

- 不重做书单首页和详情页整体视觉体系，不回退底部 Liquid Glass 添加入口。
- 不把内容卡片、书籍 Item、收藏理由、年度点评做成 Liquid Glass。
- 不改变普通书单排序、移出、删除、收藏理由等已对齐行为。
- 不新增与 Android 不一致的数据库 schema，除非实现阶段通过双端对照明确证明必要并获得确认。
- 不把微信读书导入扩展为通用网页书单抓取器。
- 不在本计划中实现云同步、账号级协作或跨端冲突合并。

## Decisions

### 1. 先做完整添加链路和占位书，再做微信读书导入

占位书是多个能力的共同底座。Android 在线搜索、手动创建到书单、微信读书书单导入都会产生 `is_deleted = 1` 的书籍关系。如果先做微信读书导入，iOS 将只能创建一批用户无法理解和恢复的“幽灵书籍”。因此实施顺序必须是：

```text
完整添加来源
    ↓
占位书展示与恢复
    ↓
微信读书导入
```

替代方案是把微信读书导入先做成本地书匹配，不保存占位书。该方案会丢失 Android 业务意图：用户从外部书单收集未入库书籍，并在未来决定是否加入书架。

### 2. iOS 用“加入书架/开始阅读”表达占位书恢复，不照搬 Android 的“添加”

Android 在书单内对软删除书使用 `添加` 角标，但 iOS 需要避免语义混乱。占位书已经存在于书单中，用户真正要做的是把它恢复为书架中的有效书。产品文案建议：

- 若恢复仅改变 `book.is_deleted` 和书架排序：使用 `加入书架`
- 若恢复同时将阅读状态改为在读：使用 `开始阅读`

实现阶段必须核对 Android `addBookToRead` 的具体写入字段、排序策略、阅读状态策略，再确定 iOS 文案。若 Android 只做取消软删除但不强制在读，优先使用 `加入书架`。

### 3. 书籍选择器扩展，而不是在书单详情重写搜索与创建流程

当前 iOS 已有 `BookPickerConfiguration`、`BookPickerViewModel`、`BookPickerView` 和书籍编辑/搜索能力。书单详情应继续通过配置驱动选择器，而不是在详情页内直接拼在线搜索、手动创建和多选逻辑。

需要扩展的方向：

- `BookPickerScope` 支持本地与在线组合搜索。
- `allowsCreationFlow` 对书单添加场景开放。
- picker result 可以表达本地有效书、在线候选、手动创建结果、占位书草稿。
- 书单详情 ViewModel 只消费标准化结果，并调用 Repository 保存 relation。

这样能保持导航职责清晰，也符合 ViewModel 不直接访问网络或数据库的规则。

### 4. 微信读书导入采用预览确认，而不是静默创建

Android 系统分享导入是直接解析并保存。iOS 应改成更安全的两步：

```text
输入/接收链接
    ↓
Repository 解析为 ImportPreview
    ↓
导入预览 Sheet
    ↓
用户确认保存
    ↓
创建书单 + 占位书 relation
```

预览必须显示书单标题、简介、书籍数量、每本书标题/作者/推荐语预览，以及可能的解析异常。这样可以避免微信网页结构变化时直接写入坏数据。

入口设计分两阶段：

- 第一阶段：在书单首页或书单更多菜单提供 `导入微信读书书单`，用户粘贴链接。
- 第二阶段：如果项目已有系统分享入口，再把相同 Repository 能力接入系统分享分发。

### 5. 当前书单导出必须锁定范围，不继承 Android 的全书架退化歧义

Android 当前书单导出通过传入 bookIds 启动通用批量导出页，但如果导出页自身允许清空选择并退化为全部书籍，会造成范围歧义。iOS 的 `导出此书单` 必须始终表达当前书单上下文：

- 标题使用 `导出此书单` 或 `导出“书单名”`
- 初始范围为当前书单有效书籍
- 用户不能在这个入口无意切换为全书架导出
- 空书单进入导出时必须提示无法导出，而不是生成空文件后说成功

导出字段建议默认包含书籍基本信息与书单 relation 文本。普通书单 relation 字段展示为 `收藏理由`，年度书单 relation 字段展示为 `年度点评`。如果后续导出模块已有字段选择能力，可以把 relation 文本作为默认勾选项。

### 6. 分享长图是表达型输出，导出是结构化输出，两者不合并

分享长图面向传播和展示，导出面向备份、整理和二次处理。两者共享书单快照数据，但 UI、文件格式和反馈不同：

- 分享长图：视觉模板、封面、书单标题、简介、数量、书籍条目、评分、relation 文本，走系统分享。
- 批量导出：结构化文件、字段范围、导出结果文件，走导出模块。

入口都属于书单对象级操作，放在书单详情右上角更多菜单。底部 Liquid Glass 仍只保留高频 `添加书籍`。

### 7. 年度本体说明使用“年度寄语/年度说明”，不复用普通书单“简介编辑”

Android 年度书单允许编辑 desc，但 UI 语义没有与普通书单拉开。iOS 应明确三层：

- 年度书单标题：由年份/系统生成，不允许用户改。
- 年度书单成员：由读完记录自动同步，不允许手动添加、移出、排序。
- 年度本体说明：用户可以写 `年度寄语` 或 `年度说明`，表达这一年的阅读总结。
- 年度单本书 relation：继续使用 `年度点评`，表达这本书在年度中的个人记录。

入口建议放在年度书单详情更多菜单：`编辑年度说明`。展示位置放在 Header 简介区，避免进入书籍 Item relation 区造成语义混淆。

### 8. 记住书单分组选择属于 UI 偏好，不进入数据库 schema

iOS 已有 `BookCollectionDisplaySettingStore` 保存书单显示偏好。最近选择的 `manual/annual` 应归入同一个轻量设置对象或相邻轻量设置存储，不应写入业务数据库。进入书单首页时：

- 若本地偏好为 `annual` 且年度书单非空，默认显示年度书单。
- 若本地偏好为 `annual` 但年度书单为空、手动书单非空，回退到手动书单。
- 若用户主动切换分组，立即保存偏好。

### 9. UI 与组件归位

- 页面壳层继续归 `xmnote/Views/Book/`。
- 页面私有组件继续放在 `xmnote/Views/Book/Components/BookCollectionVisualComponents.swift`，除非形成跨页面复用才迁入 `UIComponents`。
- 新增 Sheet 放在 `xmnote/Views/Book/Sheets/`。
- 书籍封面统一使用 `XMBookCover`。
- 生产文本使用 `AppTypography` 与语义色。
- Liquid Glass 只保留在顶部导航、更多菜单系统控件和底部真实交互浮层，不进入导入预览列表、导出内容区或分享模板正文。

## Risks / Trade-offs

- 微信读书网页结构变化 → 解析器必须隔离在 Repository/Service 层，导入前必须预览，失败时不得写入半成品书单。
- 占位书恢复破坏书架排序或阅读状态 → 实现前必须逐项核对 Android `addBookToRead` 的写入字段和 iOS 书架新增书排序策略，恢复操作必须在事务内完成。
- 在线搜索/手动创建结果与本地已有书重复 → 需要在预览或保存阶段给出去重策略，至少按本地既有 Repository 的重复判定规则处理。
- 当前书单导出字段与 Android 不完全一致 → 这是有意改进；iOS 必须保留 Android 的书籍导出能力，同时可额外包含 relation 文本，但要在导出说明中明确。
- 分享长图可能引入渲染性能问题 → 长书单应限制首屏分享数量或使用分页/长图渲染策略，生成过程必须有可感知进度和失败反馈。
- 年度说明与年度点评语义混淆 → 文案、入口和展示位置必须分层；不得把年度说明入口放进书籍 Item。
- 分组记忆可能进入空年度页 → 加载快照后按空数据回退规则修正显示分组。

## Migration Plan

1. 核对 Android 与 iOS 数据事实：`book.is_deleted`、`collection_book.recommend`、`collection.desc`、书架排序、阅读状态写入、导出字段范围。
2. 扩展添加书籍链路和占位书模型，完成本地/在线/手动创建结果统一保存。
3. 实现占位书展示、打开和恢复；验证不会破坏普通书单现有书籍 Item。
4. 接入微信读书导入预览与保存，先做应用内粘贴链接入口，再考虑系统分享入口。
5. 升级 `导出此书单` 为真实导出流程，并保留空态、失败态和字段说明。
6. 增加分享长图能力，复用书单快照数据但独立于结构化导出流程。
7. 增加年度说明编辑与展示，保持年度成员自动同步和单本年度点评不变。
8. 增加书单分组选择偏好。
9. 最后统一做构建校验和手动场景核查。

回滚策略：每个能力应尽量以独立入口开关或独立 UI 分支实现。若导入、导出、分享出现问题，可回退对应入口或恢复占位反馈，不影响既有书单详情阅读、排序和收藏理由能力。

## Open Questions

- 占位书恢复是否必须把阅读状态设为 `在读`，还是只恢复到书架并保持默认状态？需要以 Android 写入事实为准。
- 当前书单导出的默认格式应沿用现有书籍导出模块，还是为书单关系新增专门模板？
- 分享长图是否需要包含全部书籍，还是长书单限制数量并提示“仅展示前 N 本”？需要结合性能与分享场景确定。
- 微信读书导入若遇到本地已有同名同作者书籍，默认复用本地书还是保留占位书？建议优先复用本地有效书，但需要和 Android 对齐策略核对。
- 年度本体说明最终文案使用 `年度寄语` 还是 `年度说明`？当前设计推荐 `年度寄语`，更贴近年度总结语境。
